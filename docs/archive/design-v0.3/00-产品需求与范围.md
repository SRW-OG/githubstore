# 00 · 产品需求与范围

> 状态：草案 v0.3（设计阶段，未开发）
> **v0.3 变更（2026-10-18）**：**架构改为单一 C# 进程**——XAML 做界面，C# 写全部业务逻辑，**不再使用 Go**。原 v0.2 的「C# UI 进程 + Go 核心进程 + 命名管道 IPC」方案作废（见 docs/03 附录 A）。连带修订：NFR-1.x 全部改为**单进程口径**、约束 C-1、§7 范围外新增两条。
> **v0.2 变更**：界面技术栈确定为 **WinUI 3（Windows App SDK）**，NFR-1.4 / NFR-1.6 / C-1 已修订。
> 适用范围：GitHubStore —— 以 GitHub 开源软件为数据源的 Windows 应用商店客户端
> 编写时间：2026-10

---

## 本章结论（TL;DR）

1. **产品定位**：一个「开源的软件商店客户端」，把 GitHub 上能装到 Windows 的软件，做成可分类浏览、可排名、可搜索、可一键安装/更新/卸载的商店体验。它不托管二进制，只做**发现 + 安装编排 + 生命周期管理**。
2. **差异点不是「商店」，而是「安装路径可控 + 绿色安装 + AI 说明」**：winget / Store 的痛点是路径不可选、说明看不懂、装完不知道装到哪；本产品把这三件事做成主路径。
3. **技术栈：单进程 C# + WinUI 3**。XAML 做界面，C# 写业务逻辑，**没有 Go、没有 IPC、没有第二个进程**（安装器子进程除外，那是被安装的第三方程序本身）。好处是**单栈、简单、调试直观**；代价见第 4 条。
4. **必须正视的代价**：① **丧失崩溃隔离**——第三方安装器若崩溃/挂起，虽在独立子进程中不会直接带崩主进程，但主进程仍需处理超时与僵尸子进程；② **无跨平台可能**（Go 有，C# 没有）；③ **内存不占优**——WinUI 3 + .NET 空窗口基线就要 60–90MB，这是原生 .NET 框架的成本，不是实现问题。**「少占资源」仍是目标，但口径已从「极致」调整为「同量级里最克制」。**
5. **不做的事要写死**：不做应用托管/分发、不做破解与激活、不静默提权、不做账号体系与支付、**不做无 UI 的静默安装入口**、**不做「忽略校验」开关**。范围外清单见 §7，它是需求变更的挡箭牌。
6. **风险最高的一条**：第三方安装器的静默参数与自定义路径支持极不一致（见 docs/06 ADR-004）。产品必须允许「该包不支持自定义路径」这一事实存在，并把选择权透明地交给用户，而不是假装成功。
7. **第二高风险**：WinUI 3 依赖 .NET 与 Windows App SDK 运行时，安装包无法压到 20MB（ADR-009 已修订为 ≤40MB）。这需要负责人明确接受（**Q-6**），否则应回到 WebView 方案。

## 1. 问题陈述

### 1.1 用户当前的路径有多烂

| 场景 | 现在怎么做 | 痛点 |
|---|---|---|
| 想找一个 Windows 上能用的开源工具 | 逛 GitHub Trending / 知乎推荐 / 各种「Awesome 列表」 | 信息分散、没有「能不能装」的判断、不知道最新版在哪 |
| 装一个开源软件 | 进 Releases 页，在一堆 `Source code (zip)` 里找 `-setup.exe` | 资产命名混乱、容易下错架构、没有校验 |
| 想装到 D 盘 | 安装器给了选项就点，没给就只能装 C 盘 | 系统盘爆满；便携软件被迫写注册表 |
| 装完想更新 | 记不住装过什么，逐个去 Releases 看 | 更新发现成本极高 |
| 装完想卸载 | 控制面板里一堆 `Unknown Publisher` | 不知道哪个是哪个，残留目录清不干净 |
| 想搞懂这软件干嘛的 | 读 README，中英混杂，动辄几千行 | 决策成本高，尤其对非开发者 |

### 1.2 目标用户

| 画像 | 描述 | 关键诉求 | 占比预估 |
|---|---|---|---|
| **P1 折腾型开发者** | 装一堆 CLI/GUI 工具，喜欢便携版和自定义路径 | 绿色安装、路径可控、版本清晰 | 40% |
| **P2 有洁癖的效率用户** | 不是程序员，但会用开源软件替代商业软件 | 分类浏览、AI 一句话说清、一键装 | 35% |
| **P3 内网/低配机用户** | 老机器、内存小、网络差 | 省资源、离线缓存、能配代理 | 25% |

> **结论**：P1 决定「安装路径」必须是主功能而不是高级选项；P3 决定 NFR-1 不是口号，而是会掉用户的功能。
>
> **v0.2 补充**：WinUI 3 的运行时依赖会**伤害 P3**（老机器可能缺 .NET 或 Windows App SDK）。缓解手段：安装器内置运行时检测与引导、提供「精简模式」（减少动效与图片）；若实测 P3 转化率过低，需重新评估 Q-6。

### 1.3 核心使用场景（User Story）

- **US-1 发现**：作为 P2，我想按分类和 Star 排名逛，5 分钟内找到 2 个能用的软件。
- **US-2 判断**：作为 P2，我不想读 3000 行 README，我想看 5 行 AI 总结就知道这软件干什么、适不适合我。
- **US-3 安装**：作为 P1，我要把软件装到 `D:\Tools\xxx`，或者干脆绿色解压不写注册表。
- **US-4 兜底**：作为 P1，当某个包只能走 winget 且不支持自定义路径时，我要**在点安装前就知道**，而不是装完才发现。
- **US-5 管理**：作为 P1，我想在一个列表里看到「我装了什么、哪些有更新、哪些是商店装的」，并一键更新。
- **US-6 搜索**：作为 P2，我输入「截图」或「jie tu」，要能搜到截图工具。
- **US-7 低配**：作为 P3，我希望它常驻托盘只吃几十 MB，而不是一个浏览器。

## 3. 非功能需求（NFR）

> **v0.3 修订说明**：架构改为**单进程 C#**，全部 NFR-1.x 改为**单进程口径**——只统计 `githubstore-ui.exe` 一个进程（安装器子进程是第三方程序，单独记录峰值但不计入本表）。
> **为什么不把「进程组」继续作为口径**：单进程后「进程组」概念只对安装器子进程有意义，而那是第三方程序在跑，不是我们的代码。把自己的内存账和「被我们启动的第三方程序」混在一起统计，只会让指标失真。
> 数值均为**估算，需实测回填**（口径见 docs/03 §3.5、docs/08 §6：`WorkingSet64` 与 `PrivateMemorySize64` 分别报告，不混用）。

| 编号 | 维度 | 指标 | 目标 | 上限 | 备注 |
|---|---|---|---|---|---|
| NFR-1.1 | 内存 | **托盘空闲**（`githubstore-ui.exe` 单进程） | ≤110 MB WS / ≤160 MB PM | 150 MB WS / 210 MB PM | 窗口隐藏但进程驻留；不含安装器子进程 |
| NFR-1.2 | 内存 | **浏览列表态**（单进程） | ≤170 MB WS / ≤230 MB PM | 220 MB WS / 300 MB PM | 1000 条数据稳态 |
| NFR-1.3 | 内存 | **下载+安装并发态**（单进程） | ≤200 MB WS / ≤270 MB PM | 260 MB WS / 340 MB PM | **不含**安装器子进程（单独记录峰值） |
| NFR-1.4 | 磁盘 | 安装包体积（**不含 .NET 运行时**） | **≤40 MB** | **60 MB** | v0.1 的 20MB 已不可达（ADR-009） |
| NFR-1.5 | 磁盘 | 缓存上限（可配） | 512 MB | 2 GB | 超限 LRU 清理 |
| NFR-1.6 | 启动 | 冷启动到可交互 | **≤2.0 s**（首次） | 3.0 s | 首次含 .NET / WinUI 初始化 |
| NFR-1.6b | 启动 | 热启动到可交互 | ≤1.2 s | 2.0 s | 运行时已就绪 |
| NFR-1.7 | CPU | 空闲 CPU | ≈0% | 1% | 无轮询、事件驱动 |
| NFR-2.1 | 性能 | 本地搜索 P95 | ≤50 ms | 120 ms | 2 万条索引 |
| NFR-2.2 | 性能 | 分类切换 | ≤100 ms | 200 ms | |
| NFR-2.3 | 性能 | 列表滚动 | 60 fps | 45 fps | 虚拟滚动 |
| NFR-3.1 | 可靠性 | 安装事务原子性 | 无「半装」状态 | — | journal 可恢复 |
| NFR-3.2 | 可靠性 | 崩溃率 | <0.1% 会话 | — | |
| NFR-4.1 | 安全 | 二进制校验 | 100% 强制 | — | 签名+哈希 |
| NFR-4.2 | 安全 | 提权 | 单次 UAC；仅校验通过的文件可提权 | — | 见 docs/07 |
| NFR-5.1 | 隐私 | README 默认不出本机 | 是 | — | 本地模型默认 |
| NFR-5.2 | 隐私 | Token 加密存储 | DPAPI | — | 不落日志 |
| NFR-6.1 | 兼容 | OS | Win10 1809+ / Win11 | — | **需 .NET 运行时 + Windows App SDK Runtime** |
| NFR-6.2 | 兼容 | 架构 | x64 + arm64 | — | |
| NFR-6.3 | 兼容 | DPI | 100%–250% 无错位 | — | 每显示器 DPI 感知 |
| NFR-7.1 | 可维护 | 单测覆盖核心域 | ≥70% | — | 安装状态机、版本比较、路径校验 |
| NFR-8.1 | 可用性 | 离线可用 | 浏览+搜索可用 | — | 安装需网络 |

> **读法**：NFR-1.x 是**可验收的硬指标**，每个里程碑都要跑基准（方法见 docs/03 §3.5、docs/08 §6）。
> **两个必须写进验收口径的前提**：① 口径是**单个 `githubstore-ui.exe` 进程**，不是「进程组」，也不是「系统总和」；② 安装器子进程（我们 `Process.Start` 起来的第三方 exe）**不计入** NFR-1.3，但要在测试报告里单独列出峰值——这是为了区分「我们的代码占多少」与「被安装的程序占多少」，否则指标会变成一个无法归因的混合数字。

## 4. 关键设计约束（会传导到架构）

| 约束 | 影响 |
|---|---|
| ~~C-1 二进制必须能一次下载就跑，不依赖运行时~~ **（v0.2 已失效）** | WinUI 3 需要 .NET Runtime + Windows App SDK Runtime。改为 **C-1'：安装器必须能检测并引导安装所需运行时**（ADR-009） |
| ~~C-1a Go 无 WinUI 3 绑定~~ **（v0.3 已失效）** | v0.3 架构不再使用 Go，该约束不存在了。取而代之：**C-1b 单栈 C#**——XAML 界面 + C# 业务逻辑，无跨语言边界、无 IPC |
| C-2 安装/卸载涉及系统写操作 | 必须有提权边界（docs/06 ADR-006、docs/07）；v0.3 为「`Verb=runas` 直启安装器」，仅校验通过的文件可提权 |
| C-3 第三方安装器行为不可控 | 必须有「能力探测 + 降级」而不是「假设成功」（docs/06） |
| C-4 GitHub 无 SLA、有配额 | 必须离线优先 + 条件请求 + 缓存（docs/05） |
| C-5 用户机器可能缺 .NET / Windows App SDK 运行时 | 必须检测并引导安装；失败要有明确文案而非崩溃 |
| C-6 商店不能替用户「同意」第三方许可 | 首次安装需显式勾选来源与许可提示 |
| ~~C-7 双进程需定义 IPC 契约~~ **（v0.3 已失效）** | 单进程后无 IPC。取而代之：**C-7' UI 线程纪律**——所有 IO/安装/搜索必须在后台，UI 线程禁止阻塞（docs/03 §3.4） |
| ~~C-8 UI 与 Core 需各自签名并互相校验~~ **（v0.3 已失效）** | 单进程后只有一个二进制，无需互相校验。取而代之：**C-8' 单二进制签名 + 更新链校验**——自更新必须校验新版本签名（docs/03 §3.7） |
| **C-9 安装器是独立子进程** | 主进程必须能处理「子进程挂起/崩溃/僵尸」，不能假定它会正常退出（docs/06 §5） |
| **C-10 单进程无崩溃隔离** | 第三方安装器虽在子进程，但本进程内任何 `async void` 未捕获异常都会终止整个应用；必须全局兜底 + 崩溃上报（docs/08 §9.1） |

## 7. 范围外（明确不做）

1. **不托管、不镜像、不再分发**任何第三方二进制；下载一律来自上游官方地址。
2. **不做账号体系、支付、订阅、评分评论**（评分仅本地展示 GitHub Star，不引入自有评分）。
3. **不提供破解、激活、绕过授权**的功能；License 非 OSI 认可时标注并警告。
4. **不静默提权**、不绕过 UAC、不写驱动、不常驻服务。
5. **不接管系统更新**、不替代 Windows Update。
6. **不做移动端/Web 端**；不做 Linux/macOS（架构上不排除，但不在范围）。
7. **不做「一键装全家桶」**式的批量脚本执行。
8. **不做 AI 生成安装脚本**（模型输出永不进入执行路径）。
9. **不提供无 UI 的静默安装入口**——包括命令行参数、URL scheme、深链接。原因：一旦存在「不弹窗就能装」的通道，应用就变成了无门槛的提权服务。**任何「方便脚本/自动化」的诉求都必须走 UI 确认。**
10. **不提供「忽略校验」开关**——不是默认关闭，而是**代码中不存在**。`VerifyPolicy.HardFail` 时只有「报告问题 / 复制诊断 / 查看详情」三个无安装能力的入口（docs/07 §11.1 红线）。

## 8. 术语表

| 术语 | 定义 |
|---|---|
| AppId | 商店内应用唯一标识，由客户端分配的 `SourceInstanceId` 与源内 `PackageId` 组成；仓库 URL 仅用于重复提示，见 docs/01 与 docs/10 |
| 通道 Channel | 安装方式：`Http`（直下 Release 资产）/ `Winget` |
| 策略 Strategy | 安装位置语义：`Default` / `Custom` / `Green` |
| 能力 Capability | 某个包实际支持的安装选项集合（由探测得出，不是猜的） |
| 绿色安装 | 解压即用、不写系统注册表、卸载即删目录 |
| 指纹 Fingerprint | 判定「这条已安装记录是否由本商店创建」的标识集合 |
| Origin | 安装来源：`Store` / `External` |
| 包能力矩阵 | 包类型 × 安装策略 的可行性表，见 docs/06 §4 |
| **单进程分层** | `App`（XAML/ViewModel）→ `Core`（业务服务）→ `Platform.Win32`（P/Invoke），依赖单向，见 docs/02 ADR-011 |
| **`runas` 直启** | 提权方式：`Process.Start` + `Verb="runas"` 直接启动安装器本体，不保留中间提权进程，见 docs/06 ADR-006 |

## 9. 待确认（需产品/技术负责人拍板）

> **单一真源**：完整清单（含选项、建议、是否阻塞里程碑）在 `09-决策记录与路线图.md` §3。本节只列**阻塞 M0/M1 开工**的问题。

| 编号 | 问题 | 建议 | 阻塞 |
|---|---|---|---|
| **Q-6** | **是否接受 WinUI 3 的代价：安装包 ≤40MB + 需装 .NET / Windows App SDK 运行时** | 必须明确拍板。接受则按 ADR-009 走；不接受则需重新评估技术栈（WPF 可压到 30MB 但仍需 .NET） | **M0 出口** |
| **Q-17** | **无签名的开源安装器无法提权安装（装不到 `Program Files`）是否可接受** | **建议接受**——这是 ADR-006「只有校验通过才 runas」的必然结果；放宽规则会摧毁唯一防线 | **建议 M0 一并拍板** |
| Q-1 | 首版是否包含 winget 通道 | 两条都做，winget 作为「无资产时的兜底」 | M2 |
| Q-3 | 是否内置种子目录 | **已裁决**：内置 gzip JSON 快照（≤1.5MB，500 条） | 已裁决 |
| Q-4 | 托盘常驻 vs 关窗即退 | **已裁决**：默认隐藏到托盘，设置可切「关窗即退出」 | 已裁决 |
| Q-8 | 默认安装根目录 | `%LOCALAPPDATA%\Programs`（免 UAC） | M1 |
| Q-2 | AI 摘要默认行为 | **已裁决**：默认关闭 + 入口始终可见 + 首选本地 Ollama | 已裁决 |

> **结论**：Q-6 与 Q-17 是仅有的两个「接受代价」型决策，都是 WinUI 3 + 单进程架构的必然结果——前者是体积与运行时依赖，后者是无签名软件装不到系统目录。回避它们，后面的里程碑都会带着未承认的债。
