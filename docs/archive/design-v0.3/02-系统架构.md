> 状态：草案 v0.3（设计阶段，未开发）

> 下游：`03`（技术选型）、`04`（UI）、`05`（数据源/AI）、`06`（安装引擎）、`07`（安全）、`08`（测试）

## 本章结论（TL;DR）

1. **只有一个进程**：`githubstore-ui.exe`。XAML 是界面，C# 是业务逻辑，两者在同一进程内的不同线程/任务上运行。**没有 IPC、没有第二个二进制、没有跨语言边界。**
2. **唯一的「第二个进程」是被安装的第三方程序**：安装器（MSI/NSIS/Inno/…）本来就是别人的 exe，我们只是 `Process.Start` 它。这不是我们的架构组件，是产品要处理的对象。
3. **单进程的核心风险从「IPC」变成了「UI 线程」**：v0.2 最担心的是管道断连与协议兼容；v0.3 最担心的是**某个 `async` 方法不小心在 UI 线程上同步等待**，把界面卡死。因此本章用一整节（§4）规定线程纪律，这是 v0.3 最重要的工程约束。
4. **丧失崩溃隔离，必须用别的方式补偿**：第三方安装器在独立子进程里，所以它崩溃不会带崩我们；但**我们自己的 `async void` 未捕获异常会直接终止应用**。补偿手段：全局异常兜底（`AppDomain.UnhandledException` / `TaskScheduler.UnobservedTaskException` / `Application.UnhandledException`）+ journal 恢复 + 崩溃转储。
5. **分层是唯一的结构复杂度**：UI 层（XAML/ViewModel）→ 服务层（业务接口）→ 基础设施层（SQLite/HTTP/Process）。分层的目的不是「架构好看」，而是**让业务逻辑可以在没有 UI 的情况下被测试**——这是单进程架构里保证质量的关键。
6. **部署形态**：非打包（unpackaged）+ framework-dependent，目标 ≤40MB（ADR-009）。选择 unpackaged 是为了简化商店自身的传统分发、文件布局与独立更新器集成；第三方软件能否自定义安装路径由其安装器能力决定，与商店自身是否 MSIX 无关。

│  │   DispatcherQueue   │◄──────►│                         │   │

│                                │  VerifyService          │   │
│                                └───────────┬─────────────┘   │
│                                            │                 │
│                                ┌───────────▼─────────────┐   │
│                                │  基础设施                │   │

│                                │  Win32 (托盘/签名)       │   │

└───────────────────────────────┬──────────────────────────────┘
                                │ Process.Start
                                ▼
              ┌──────────────────────────────────┐
              │  第三方安装器（不是我们的代码）      │

> **结论**：架构图上唯一的「外部进程」是第三方安装器。它是**被管理的对象**，不是架构组件——这一点与 v0.2 有本质区别：v0.2 的 Go 核心进程是我们自己的代码，需要协议、生命周期、版本协商；v0.3 的安装器进程是别人的程序，我们只需要**启动、等它、超时杀它**。

### 1.2 与 v0.2 的差异（为什么删掉了那些东西）

| v0.2 有 | v0.3 | 为什么删 |
|---|---|---|
| `githubstore-core.exe`（Go 核心） | ❌ 无 | 用户要求 C# 写业务，单栈更简单 |
| `gs-elevate.exe`（Go 提权进程） | ❌ 无 | 改为 `Verb="runas"` 直启安装器（docs/06 ADR-006） |
| 命名管道 + JSON 帧（ADR-008） | ❌ 无 | 同进程无需序列化 |
| 协议版本协商 / 握手 | ❌ 无 | 不存在跨版本通信 |
| UI↔Core 互相校验 | ❌ 无 | 只有一个二进制 |
| 托盘归 Core（ADR-010） | ❌ 改为**本进程创建托盘** | 单进程下托盘只能由本进程持有（见 §5.2） |
| 崩溃隔离（安装器崩溃不影响 UI） | ⚠️ **部分保留** | 安装器仍在子进程，但本进程内异常会终止整个应用 |

> **结论**：v0.3 删掉的是「为跨语言边界付出的全部复杂度」，保留的是「为第三方不可控代码付出的防御」。**净效果是结构更简单，但内存与跨平台能力下降**。

## 2. ADR-011：单进程分层架构

| 项 | 内容 |
|---|---|
| **背景** | 用户指定「XAML 做界面、C# 写业务逻辑」。v0.2 的双进程方案是为「Go 写业务 + WinUI 3 写界面」设计的，前提已不成立。 |
| **备选** | ① 单进程分层（UI 层 / 服务层 / 基础设施层）；② 单进程但扁平（所有代码在 MainWindow 里）；③ 保留双进程（C# UI + C# Core，用 IPC 或 `AssemblyLoadContext` 隔离）。 |
| **决策** | **① 单进程三层**：`UI`（XAML + ViewModel，只做呈现）→ `Services`（业务接口与实现）→ `Infrastructure`（SQLite / HTTP / Win32 / 文件系统）。层间只通过接口依赖，构造注入。 |
| **理由** | ① **可测试性**：业务逻辑不依赖 UI，可以在 xUnit 里直接测服务层；② **可替换性**：SQLite 可换内存实现、HttpClient 可换 mock；③ **防止 UI 代码腐化**：把「什么该在服务层」用编译期依赖方向固定住（UI 可以引用 Services，Services 不能引用 UI）。 |
| **后果（正）** | 结构简单、调试直观、启动快、无序列化开销、单栈维护。 |
| **后果（负）** | ① **无进程级隔离**：服务层的一个未捕获异常可终止整个应用；② **无跨平台可能**；③ 分层靠纪律维持，没有编译期强制（可用架构测试补：如 `NetArchTest.Rules` 断言 `Services` 不引用 `Microsoft.UI.Xaml`）。 |
| **回退条件** | 若「本进程内某个非 UI 组件频繁导致崩溃」且无法通过异常边界隔离，则考虑将该组件拆为独立进程（代价是重新引入 IPC）。**这是唯一值得重新拆进程的情形**，不要因为「架构洁癖」拆。 |

### 2.1 分层与依赖方向

```
githubstore/
├─ src/
│  ├─ GitHubStore.App/               ← 可执行，WinUI 3
│  │   ├─ App.xaml(.cs)              应用启动、DI 装配、全局异常兜底
│  │   ├─ Views/                     XAML 页面与控件
│  │   ├─ ViewModels/                ViewModel（只依赖 Services 接口）
│  │   ├─ Converters/                XAML 值转换器
│  │   └─ Services/                  仅「纯 UI 能力」实现：文件夹选择器、剪贴板、Shell 打开
│  │
│  ├─ GitHubStore.Core/              ← 类库，**不引用任何 WinUI 类型**
│  │   ├─ Abstractions/              所有服务接口 + 领域模型（对应 docs/01）
│  │   ├─ Catalog/                   收录、分类、排名
│  │   ├─ Search/                    FTS5 查询构建、分词
│  │   ├─ Install/                   安装计划、执行、journal、状态机
│  │   ├─ Inventory/                 已安装扫描、更新检查
│  │   ├─ Download/                  HttpClient、断点续传
│  │   ├─ Verify/                    哈希、签名、策略判定
│  │   ├─ Summary/                   AI 摘要、提供商抽象
│  │   └─ Data/                      SQLite 仓储、迁移
│  │
│  ├─ GitHubStore.Platform.Win32/    ← 类库，Win32 P/Invoke 集中地
│  │   ├─ Tray/                      Shell_NotifyIcon
│  │   ├─ Signing/                   WinVerifyTrust
│  │   └─ Shell/                     快捷方式、关联、打开目录
│  │
│  └─ GitHubStore.Tests/             ← xUnit
│
└─ docs/
```

**依赖方向（硬规则，用架构测试强制）**：

| 从 ↓ 可以引用 → | App | Core | Platform.Win32 | Tests |
|---|---|---|---|---|
| **App** | — | ✅ | ✅ | ❌ |
| **Core** | ❌ **禁止** | — | ❌ **禁止** | ❌ |
| **Platform.Win32** | ❌ | ❌ | — | ❌ |
| **Tests** | ✅ | ✅ | ✅ | — |

> **为什么 `Core` 不能引用 `Platform.Win32`**：Win32 P/Invoke 是平台相关的、难测试的。`Core` 通过接口（如 `ISignatureVerifier`、`ITrayController`）声明需求，由 `App` 在 DI 装配时注入 `Platform.Win32` 的实现。这样 `Core` 可以在任何环境下单测。
>
> **为什么 `Core` 不能引用 `App`**：这条是最重要的——它保证「业务逻辑不知道 UI 的存在」。一旦允许反向引用，业务代码里就会出现 `MessageBox.Show`，然后整个可测试性崩塌。

> **结论**：分层不是为了好看，是为了**让 `Core` 在没有窗口的环境里能跑测试**。这也是 docs/08 测试策略的基础。

## 4. 线程与并发模型（**v0.3 最重要的工程约束**）

### 4.1 执行位置约定

| 任务类型 | 执行位置 | 原因 |
|---|---|---|
| XAML 布局/绘制、输入、无障碍 | **UI 线程**（`DispatcherQueue`） | WinUI 强制要求 |
| ViewModel 的属性/集合变更 | **UI 线程** | `ObservableCollection` 非线程安全 |
| SQLite 查询 | **线程池**（`Task.Run` 或 `async`） | `Microsoft.Data.Sqlite` 是同步 API，会阻塞调用线程 |
| HTTP（GitHub / 下载 / AI） | **线程池**（`HttpClient` 原生 async） | 纯 IO，不占线程等待 |
| 哈希/签名校验 | **线程池**（`Task.Run`） | CPU 密集且可能数秒 |
| **安装器执行** | **独立子进程**（`Process.Start`） | 第三方代码不可控，隔离它能防止我们被它拖死 |
| AI 流式解析 | **线程池** | 读流是 IO |

### 4.2 UI 线程纪律（五条硬规则）

1. **禁止 `.Result` / `.Wait()` / `.GetAwaiter().GetResult()`**。在 UI 线程上同步等待一个需要回到 UI 线程的 `Task` 会**必然死锁**。代码审查时一律拦。
2. **服务层方法全部 `async` 且接受 `CancellationToken`**。没有例外的同步业务方法（`IsInstalled` 这类纯内存判断除外）。
3. **进度回报用 `IProgress<T>`**。`Progress<T>` 在构造时捕获 `SynchronizationContext`，`Report()` 会自动 marshal 回 UI 线程——这是唯一正确的跨线程更新方式。
4. **服务层内部一律 `ConfigureAwait(false)`；UI/ViewModel 层不写**。UI 层需要回到 UI 线程继续操作控件，写了反而出错。
5. **`async void` 只允许出现在事件处理器**，且必须自带 try/catch。其他任何地方用 `async Task`。遗漏的 `async void` 异常是无法捕获的——它会直接终止进程。

### 4.3 子进程执行模型（M-11 ProcessRunner）

安装器是我们无法信任的第三方代码。必须遵守：

```
启动 → 注册输出读取 → await WaitForExitAsync(ct) → 处理退出码
         ↓
    无输出超时监控（心跳）
         ↓
    超时/取消 → 停止等待并记录 Unknown/Partial → 后台或下次启动对账
```

**必须实现的防御**：

| 风险 | 表现 | 对策 |
|---|---|---|
| **stdout 管道死锁** | 子进程写满管道缓冲区后阻塞，我们等它退出 → 双方互等 | 用 `OutputDataReceived` + `BeginOutputReadLine()` 异步消费；或 `ReadLineAsync` 循环配合 `WaitForExitAsync`。**绝不能先 `WaitForExit()` 再读输出** |
| **安装器挂起** | 卡在某个对话框或网络等待 | 心跳超时（如同阶段 10 分钟无输出）→ 提示用户「可能卡住」→ 允许放弃等待 |
| **宿主退出而安装器仍运行** | 安装状态暂时不确定 | journal 先落盘；真实安装器不加入 kill-on-close Job Object；重启后按注册表/包管理器/目标路径对账。Job Object 只回收商店自有、可安全终止的辅助进程 |
| **句柄继承泄漏** | 子进程继承了不该有的句柄 | `UseShellExecute=false` 时手动管理；.NET 默认不继承，但 P/Invoke 调 `CreateProcess` 时需显式处理 |
| **提权进程无输出** | `Verb="runas"` 时 `UseShellExecute=true`，无法重定向 | 接受这一限制，进度靠「目标目录/注册表变化」推断（docs/06 §5.3） |

> **结论**：v0.3 里「崩溃隔离」从「进程架构保证」退化为「ProcessRunner 模块保证」。**这个模块的代码质量直接决定产品稳定性**——安装器挂起时用户看到的是「转圈不动」还是「明确提示可放弃」，全看这里。docs/08 §9.1 为此设计了专项测试。

### 4.4 DI 装配与生命周期

```csharp
// App.xaml.cs — 启动时装配
var services = new ServiceCollection();

// 基础设施（单例，全应用共享）
services.AddSingleton<IDbConnectionFactory, SqliteConnectionFactory>();
services.AddSingleton(sp => new HttpClient(new SocketsHttpHandler {
    PooledConnectionLifetime = TimeSpan.FromMinutes(10),
    MaxConnectionsPerServer = 8,
}) { Timeout = Timeout.InfiniteTimeSpan });   // 超时由 CancellationToken 控制
services.AddSingleton<ISignatureVerifier, WinVerifyTrustVerifier>();
services.AddSingleton<IProcessRunner, ProcessRunner>();

// 业务服务（单例，无状态或有内部缓存）
services.AddSingleton<ICatalogService, CatalogService>();
services.AddSingleton<ICatalogSourceService, CatalogSourceService>();
services.AddSingleton<IInstallService, InstallService>();
services.AddSingleton<IInventoryService, InventoryService>();

// ViewModel（瞬态，每次导航新建）
services.AddTransient<HomeViewModel>();
services.AddTransient<DetailViewModel>();

var provider = services.BuildServiceProvider();
```

> **为什么不用 `Host.CreateDefaultBuilder`**：Generic Host 会启动配置、日志、生命周期管理等多个后台服务，对桌面应用是**多余的内存与启动开销**（与 NFR-1.6 冲突）。用裸 `ServiceCollection` 即可，需要配置读写时自己实现 `ISettingsService`。
>
> **`HttpClient` 超时为什么设 `InfiniteTimeSpan`**：防止两套超时打架——`HttpClient.Timeout` 覆盖整个请求（含流式响应体的读取），会把 AI 摘要的长流式响应误杀。统一用 `CancellationToken` 控制，语义更清晰。

## 5. 生命周期

### 5.1 启动序列

| 阶段 | 动作 | 是否阻塞首屏 |
|---|---|---|
| 1 | `Program.Main` → `App` 构造 → DI 装配 | 阻塞 |
| 2 | 打开 SQLite（WAL）、跑迁移 | 阻塞（<100ms） |
| 3 | 显示主窗口（先渲染骨架屏） | — |
| 4 | 后台：检查上次未完成的 journal | 否 |
| 5 | 后台：加载目录缓存 → 填充列表 | 否 |
| 6 | 后台：检查运行时依赖、网络、更新 | 否 |

> **关键**：阶段 3 必须在阶段 4–6 之前完成。**任何 IO 都不能挡住首屏**——这是 NFR-1.6（≤2s 冷启动）的实现前提。

### 5.2 托盘与关窗（**v0.3 的架构性取舍**）

单进程下托盘只能由本进程创建，因此「关窗即退出」和「托盘常驻」**不可兼得**。三个方案：

| 方案 | 关窗行为 | 空闲内存 | 更新检查 | 用户体验 |
|---|---|---|---|---|
| **A 关窗即完全退出** | 进程终止，托盘消失 | 0 MB | 只能下次启动时检查 | 干净，但「商店」类应用缺少后台能力 |
| **B 关窗隐藏到托盘**（推荐） | 窗口隐藏，进程驻留 | 60–110 MB | 可后台定期检查 | 符合商店类应用预期，秒开 |
| C 关窗退出但保留快速启动 | 进程终止 | 0 MB | 无 | 需要「启动即秒开」的额外优化 |

**裁决：方案 B（关窗隐藏到托盘）**。理由：

1. **产品语义要求**：用户装的是一个「软件商店」，核心场景包含「后台检查更新并提醒」。方案 A 会让「更新提醒」变成「必须打开应用才知道」，直接砍掉 FR-8 的价值。
2. **用户已明确接受内存代价**：Q-6 的取舍是「接受 40MB 体积 + 运行时依赖」，即已认可 WinUI 3 的资源成本。
3. **P3 用户有退路**：设置项提供「关闭窗口时退出应用」开关，低配用户可切到方案 A。**默认 B，可选 A**。

**方案 B 必须实现的三件事**：
1. **隐藏窗口时释放视觉树**：不能只是 `Window.Hide()` 就认为省了内存——XAML 视觉树仍驻留。应卸载页面内容（导航到一个空白页），或至少清空 `ItemsSource`。
2. **隐藏时停止所有定时器**（NFR-1.7 空闲 CPU ≈0%）。
3. **真退出入口**：托盘菜单「退出」必须真正 `Application.Current.Exit()` + 等待后台任务取消，不能留进程。

> **结论**：这是 v0.3 相对 v0.2 的**明确退步**——v0.2 靠「托盘归 Go、UI 关窗即退」能做到 30–50MB 空闲；v0.3 单进程必须驻留 60–110MB。这个代价是「单进程 + C# 业务」这个决策的直接后果，必须写进文档而不是粉饰。

### 5.3 退出与清理

| 触发 | 行为 |
|---|---|
| 托盘「退出」 | 取消所有 `CancellationTokenSource` → 等待后台任务（≤3s）→ 若有安装进行中则二次确认 → 退出 |
| 系统关机/注销 | 听 `WM_QUERYENDSESSION`，若有安装进行中则拒绝或快速保存 journal |
| 未处理异常 | 兜底 → 写崩溃转储 → 提示重启 → 退出（不尝试恢复，避免状态错乱） |
| 强制结束（任务管理器） | 依靠 journal 恢复（启动时检测未完成安装） |

## 6. 关键数据流

### 6.1 浏览 → 安装 → 完成

```
用户点击「安装」
   ↓
DetailViewModel.InstallCommand（UI 线程）
   ↓ await
IInstallService.ProbeAsync(appId, ct)          ← 线程池：读 SQLite + 可能读注册表
   ↓ 返回 Capability（路径是否可控等）
UI 显示安装向导 Step 2（按 Capability 置灰选项）
   ↓ 用户确认
IInstallService.PlanAsync(request, ct)          ← 生成 InstallPlan（含 planId，写 journal）
   ↓
UI 显示 Step 3 确认页（携带 planId）
   ↓ 用户点「安装」
IInstallService.ExecuteAsync(plan, progress, ct)
   ├─ 服务层按 planId 复校 Capability 与校验结果（防绕过）
   ├─ 下载（线程池，IProgress 回报）
   ├─ 校验哈希 + 签名（线程池，CPU 密集）
   ├─ 启动安装器子进程（M-11，可 runas）
   │      ↓ await WaitForExitAsync(ct)
   ├─ 记录 journal → Done
   └─ 触发 InstalledCompleted 事件
   ↓
UI 更新任务条、列表徽标、「已安装」页
```

### 6.2 搜索

```
用户输入（200ms 防抖，UI 线程）
   ↓ await
ISearchService.SearchAsync(query, ct)           ← 线程池：SQLite FTS5 查询
   ↓
返回 CatalogPage → ViewModel 更新 ObservableCollection（UI 线程）
```

### 6.3 软件源刷新（完整快照）

```text
定时器/用户点刷新
  → ICatalogSourceService.RefreshAsync(SourceInstanceId)
  → 条件 GET source.json（ETag / Last-Modified）
  → 检查 HTTPS、源签名、密钥指纹、revision 单调性
  → 下载 index 与它引用的全部 detail 到临时缓存，逐个校验 size + SHA-256 + JSON Schema
  → SQLite 暂存表导入并构建 FTS
  → 单事务切换 catalog_sources.active_revision
  → 提交后通知 CatalogService 失效内存缓存
```

`source.json`、索引和详情都是不可信输入。任何步骤失败都只更新该源的错误状态，不修改活动 revision；浏览继续读旧快照。不同源的目录记录以 `SourceInstanceId + PackageId` 隔离。完整协议见 docs/10。

### 6.4 AI 摘要（流式）

```
用户点「用 AI 总结」
   ↓
ISummaryService.GenerateAsync(appId, progress, ct)
   ├─ 检查 summary_key 缓存 → 命中直接返回
   ├─ 未命中：调用提供商（HttpClient 流式）
   ├─ 每收到一个 chunk → progress.Report(chunk)   ← IProgress 自动回 UI 线程
   └─ 完成后写入缓存
   ↓
UI 摘要卡逐字追加
```

## 7. 资源预算与限制

### 7.1 内存度量口径（**必须写进验收**）

```powershell
# 单进程口径：只统计我们自己的进程
$p = Get-Process -Name 'githubstore-ui' -ErrorAction SilentlyContinue
if ($p) {
  [pscustomobject]@{
    WorkingSetMB = [math]::Round($p.WorkingSet64 / 1MB, 1)
    PrivateMB    = [math]::Round($p.PrivateMemorySize64 / 1MB, 1)
    Handles      = $p.HandleCount
    Threads      = $p.Threads.Count
  }
}

# 安装器子进程单独记录（不计入 NFR，但要报告峰值）
Get-Process -Name 'msiexec','setup' -ErrorAction SilentlyContinue |
  Select-Object ProcessName, @{n='WS_MB';e={[math]::Round($_.WorkingSet64/1MB,1)}}
```

**口径**：
1. 采样点 = 窗口可见且空闲 5 分钟（稳态）；
2. 对象 = **`githubstore-ui.exe` 单个进程**；
3. **同时报告** `WorkingSet64`（WS）与 `PrivateMemorySize64`（PM），两者不混用；
4. **三态目标（v0.3，估算待实测）**：

| 状态 | WorkingSet | PrivateMemory | 说明 |
|---|---|---|---|
| 托盘空闲（窗口隐藏） | ≤110 MB | ≤160 MB | NFR-1.1；视觉树应已卸载 |
| 浏览列表 | ≤170 MB | ≤230 MB | 1000 条稳态 |
| 边下边装 | ≤200 MB | ≤270 MB | **不含**安装器子进程 |

> `[待验证]` WinUI 3 空窗口基线 WS 与 .NET GC 模式（Workstation vs Server）影响很大。**任何声称「WinUI 3 更省内存」的说法都不成立**——它的成本是 .NET 运行时 + XAML 视觉树，估算 60–90MB 基线。

### 7.2 其他限制

| 资源 | 限制 | 说明 |
|---|---|---|
| HTTP 并发 | 下载 2 路、API 4 路 | NFR-1.3 |
| 安装并发 | **1**（串行） | MSI 全局互斥；且串行才能保证 journal 可解释 |
| SQLite 连接 | 1 写 + N 读（WAL） | 写操作串行化，避免 `SQLITE_BUSY` |
| 缓存上限 | 512 MB（可配） | LRU |
| 日志 | 单文件 ≤5 MB × 3 | 轮转 |
| 崩溃转储 | ≤20 MB，仅崩溃时写 | |

## 8. 离线优先与缓存层次

| 层 | 内容 | 失效 |
|---|---|---|
| L0 内存 | 当前列表、详情、Capability | 进程退出 |
| L1 SQLite | 目录、Release、资产、摘要、journal | TTL / 手动刷新 |
| L2 内置快照 | `seed-v1.json.gz`（500 条精选） | 随版本发布 |
| L3 HTTP 条件请求 | ETag / Last-Modified | 由服务端决定 |

> **结论**：离线可用性是 NFR-8.1 的要求，也是「GitHub 无 SLA」的必然应对。**单进程架构下这一层的实现反而更简单**——不需要跨进程缓存一致性。

## 9. 部署与更新形态

| 项 | 决策 | 理由 |
|---|---|---|
| 打包方式 | **unpackaged**（非 MSIX） | 便于传统分发、显式文件布局和接入独立 updater；第三方应用的安装路径能力仍由各安装器决定 |
| 运行时依赖 | framework-dependent（.NET 8 + Windows App SDK） | 自包含体积 100MB+，与 NFR-1.4 冲突（ADR-009） |
| 安装位置 | 默认 `%LOCALAPPDATA%\Programs\GitHubStore`，可改 | 免 UAC |
| 自更新 | 主程序下载并校验 → 启动独立签名 updater → 主程序退出 → updater 切换版本目录/回滚 → 重启 | 运行中的主程序不能可靠覆盖自身；独立 updater 仅负责已验证版本的原子切换 |
| 产物 | 2 个文件：`githubstore-ui.exe` + 依赖 dll，或单文件发布 | 见 docs/03 §3.7 |

> **`unpackaged` 的代价**：无法使用 MSIX 的包身份、自动更新、干净卸载。必须自己实现：卸载程序、开始菜单快捷方式、卸载注册表项（这是「商店」类应用的标准要求，不是额外负担）。
