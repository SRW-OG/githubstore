# 08 · 测试与性能基准

> 状态：草案 v0.3（设计阶段，未开发）
> **v0.3 变更（2026-10-18）**：架构由「三进程双语言（C# UI + Go Core + Go 提权）」改为**单一 C# 进程 + `runas` 直启安装器**。
> 因此：§1 分层改为 C# 单栈；**§3 契约测试（跨进程）整节删除**，其思想改为「服务接口契约测试」；§4.3/§4.4 的三进程与假提权执行器改写；§6 性能口径改为**单进程**（安装器子进程单独记录）；新增「单进程架构专属测试点」（§5.5）；§9 四道红线门禁升级为 C# 实现细节。
> 前提：单一 `githubstore-ui.exe`（C#/WinUI 3/.NET 8）。唯一外部进程是我们 `Process.Start` 起的第三方安装器。
> 定位：本文回答两个问题——**「我们凭什么相信它是对的」**（测试）与 **「我们凭什么说它省资源」**（基准）。所有 NFR 的验收口径以本文表格为准，docs/00 §3 的数字在这里变成可执行的断言。

---

## 本章结论（TL;DR）

1. **测试的主战场不是「UI 好看」，而是五件事**：版本比较（错一次就误报更新）、路径校验（错一次就删系统目录）、安装状态机（错一次就留半装状态）、**校验策略（错一次就把恶意包放进来）**、**UI 线程不阻塞**（错一次就界面假死）。前四项是纯函数/状态机，可 100% 覆盖；第五项是单进程架构的**新增必测项**，靠响应性断言 + VSTHRD 分析器保证。
2. **跨进程契约测试消失了**，但「契约」这件事没消失：服务接口（docs/01 §4）在 mock 与真实实现之间必须行为一致，否则 UI 开发用的 mock 会骗人。这叫**服务接口契约测试**（§3）。
3. **校验策略矩阵必须在三处保持一致**：docs/01 §3.7（数据契约）、docs/07 §4.3（控制项）、`tests/fixtures/verifypolicy.json`（可执行用例）。任一改动三处同 PR 更新，CI 自动比对（§2.7、TBD-08-10）。
4. **绝不用真实第三方包做集成测试**：全部用**自制假安装器**（可控地模拟成功/失败/挂起/写注册表/拒绝路径）。真实包只出现在「发布前手工抽检」里，不进 CI（§4）。
5. **提权路径在 CI 上不可测**（UAC 无法自动化），因此把「启动安装器」抽象成 `IProcessRunner`，测试用**假实现**（记录调用、返回预设）。真 UAC 只在「手动验收」清单里，且只在专用测试机上跑（§4.4）。
6. **性能基准按单进程统计**：只测 `githubstore-ui.exe`；**安装器子进程单独报告峰值，不计入 NFR**。`WorkingSet64` 与 `PrivateMemorySize64` 分别报告。
7. **门禁五条**：单测覆盖率 ≥70%（核心域）、性能回归 >15% 阻断、服务接口契约测试失败阻断、**红线 R1–R4 静态检查失败阻断（无 override）**、**策略三方比对差异阻断**。发布前 checklist 未全绿不发版（§7）。

## 1. 测试策略分层（C# 单栈）

### 1.1 分层与职责

| 层 | 测什么 | 技术 | 运行时机 | 耗时预算 | 占比目标 |
|---|---|---|---|---|---|
| **L0 单元** | 纯函数与领域逻辑：版本比较、路径校验、资产选择、状态机迁移、原因码映射、Schema 校验、校验策略 | **xUnit** + `[Theory]`/`[InlineData]` 表驱动 | 每次提交 | ≤60 s | **55%** |
| **L0b ViewModel 单元** | ViewModel 命令逻辑、状态→文案映射、格式化、导航状态机 | xUnit + 手写 fake（`ICatalogService` 等） | 每次提交 | ≤60 s | **15%** |
| **L1 服务契约** | 服务接口在 mock 与真实实现间行为一致 | 同一组 fixture 跑两遍实现（§3） | 每次提交 | ≤30 s | **10%** |
| **L2 组件** | 单模块 + 真实 SQLite（临时目录）、真实 HTTP（`HttpListener` 或 `WireMock.Net`）、真实文件系统 | xUnit + fixture | 每次提交 | ≤3 min | **10%** |
| **L3 集成** | 真实进程启动、假安装器、`IProcessRunner` 假实现、UI 响应性 | xUnit + 启动宿主进程 | 每 PR / 每晚 | ≤15 min | **5%** |
| **L4 端到端（手动）** | 对照 docs/00 FR 逐条走查，含 UAC、真实安装、AI 摘要 | 人工 + 录屏 + 检查单 | 每里程碑 / 发布前 | 半天 | **5%** |

> **结论**：占比是「用例数量」而非「代码行数」——L0 占 70% 是因为它最快最稳；L3/L4 只占 10% 却承担「能不能发版」的判断，因为只有它们能发现「真实进程 + 真实文件系统」下才出现的问题。
>
> **v0.3 相对 v0.2 的变化**：L1 从「跨语言契约」降级为「同语言接口契约」（工作量显著减少）；**新增 L0b ViewModel 层**——单进程下 UI 与业务同进程，ViewModel 的逻辑复杂度上升，不能只靠手动点。

### 1.2 工具选型

| 项 | 选择 | 理由 |
|---|---|---|
| 测试框架 | **xUnit**（首选）/ NUnit | xUnit 的 `[Theory]`/`[InlineData]` 天生适合表驱动；与 `dotnet test` 集成好 |
| 断言 | **FluentAssertions**（`[待验证]` 许可证：2025 起改为商业许可，需确认能否用于开源项目）或 xUnit 内置 `Assert` | 内置 `Assert` 完全够用且零依赖，**推荐先用内置** |
| Mock | **手写 fake**（不引 Moq/NSubstitute） | 与产品「少依赖」一致；服务接口只有 6 个，手写 fake 约 200 行 |
| 覆盖率 | `dotnet test --collect:"XPlat Code Coverage"` + ReportGenerator | 标准方案 |
| 微基准 | **BenchmarkDotNet**（仅用于纯 CPU 部分：版本比较、分词、哈希） | 唯一的第三方测试依赖，收益明确 |
| UI 自动化 | `[待验证]` **FlaUI** 或 **WinUI 3 UIA**（`Microsoft.Windows.Apps.Test`） | **WinAppDriver 已停止维护**，不要选它。需要 PoC 验证 WinUI 3 支持度 |
| 架构测试 | **NetArchTest.Rules**（或自写 Roslyn 测试） | 强制「`Core` 不引用 `App`」这类分层规则，见 §5.6 |

> **结论**：刻意「不引入重型测试框架」。理由与产品一致：测试依赖也是供应链（docs/07 §10）。唯一例外是 BenchmarkDotNet（纯 CPU 微基准无替代）与 NetArchTest（架构规则无法用手写断言表达）。

## 2. 单元测试矩阵

> 本节用例**与语言无关**，v0.3 只把代码示例改为 C#。全部为**表驱动**，新增用例只需加一行。

### 2.1 版本比较 —— ≥20 条用例

> 规则来源：docs/01 §3.4。**核心原则：宁可漏报更新，不可误报更新。**

```csharp
[Theory]
// ── 相等 ──
[InlineData("1.0.0",   "1.0.0",       0,  true)]
[InlineData("v1.0.0",  "1.0.0",       0,  true)]   // 前缀 v 忽略
[InlineData("1.0",     "1.0.0",       0,  true)]   // 缺段补 0
[InlineData("1.0.0+build1", "1.0.0+build2", 0, true)] // build 元数据忽略
// ── 升降 ──
[InlineData("1.0.1",   "1.0.0",       1,  true)]
[InlineData("1.10.0",  "1.9.0",       1,  true)]   // 数值比较，非字典序
[InlineData("2.0.0",   "1.99.99",     1,  true)]
// ── 预发布 ──
[InlineData("1.0.0-alpha", "1.0.0",   -1, true)]
[InlineData("1.0.0-beta",  "1.0.0-alpha", 1, true)]
[InlineData("1.0.0-rc.1",  "1.0.0-beta.9", 1, true)]
[InlineData("1.0.0-alpha.1", "1.0.0-alpha", 1, true)]
// ── 四段数字 ──
[InlineData("1.2.3.4",  "1.2.3.3",     1,  true)]
[InlineData("1.2",      "1.2.0.0",     0,  true)]
// ── 日期方案 ──
[InlineData("20240115", "20240114",    1,  true)]
[InlineData("2024.01.15", "2024.01.14", 1, true)]
// ── 不可比较（方案不同 / 无法解析）──
[InlineData("1.0.0",    "20240115",    0,  false)]
[InlineData("abc",      "1.0.0",       0,  false)]
[InlineData("",         "1.0.0",       0,  false)]
[InlineData("latest",   "latest",      0,  false)]
// ── 边界 ──
[InlineData("1.0.0",    "1.0.0-0",     1,  true)]  // 正式 > 预发布
[InlineData("V1.2.3",   "1.2.3",       0,  true)]  // 大写 V
[InlineData(" 1.0.0 ",  "1.0.0",       0,  true)]  // 前后空白
public void CompareVersion_Matrix(string a, string b, int expectedSign, bool comparable)
{
    var r = VersionComparer.Compare(Version.Parse(a), Version.Parse(b));
    r.Comparable.Should().Be(comparable);
    if (comparable) Math.Sign(r.Result).Should().Be(expectedSign);
}
```

**硬断言**：`Comparable == false` 时，**UI 绝不能显示「有更新」**（只能显示「版本未知」）。这条由 §2.6 的映射完整性测试兜住。

### 2.3 资产选择 —— 12 条

> 规则来源：docs/05 §9、docs/06 §3.1。**核心原则：宁可判为「无可用资产」，也不给用户下载错误的架构。**

| 场景 | 期望 |
|---|---|
| 同时有 `Setup-x64.exe` 与 `Setup-arm64.exe` | 按当前进程架构选 |
| 只有 `Setup-arm64.exe`，进程是 x64 | `ReasonNoWindowsAsset`（不猜兼容层） |
| 同时有 `Setup.exe` 与 `source.zip` | 选 `Setup.exe` |
| 只有 `source.zip` 与 `source.tar.gz` | `ReasonNoWindowsAsset` |
| 有 `.msi` 与 `.exe` | 优先 `.msi`（可静默、可控卸载） |
| 有 `.zip` 与 `.7z` | 优先 `.zip`（Windows 原生可解压） |
| `Setup.exe` vs `Setup-1.2.3.exe` | 优先带版本号的（更明确） |
| 资产名含 `debug`/`symbols`/`.pdb` | 排除 |
| 资产名含 `portable`/`standalone` | 归类为 `PortableExe` |
| 只有 checksums 文件 | `ReasonNoWindowsAsset` |
| 资产大小 0 | 排除 |
| 资产名含 `ia32`/`x86` 且进程 x64 | 记录为 `Arch.X86`，仅在无 x64 时降级使用 + 警告 |

### 2.4 安装状态机 —— 20 条

> 规则来源：docs/01 §7、docs/06 §5。**核心原则：任何非法迁移必须抛异常，不允许静默忽略。**

| # | 起始 | 事件 | 期望 |
|---|---|---|---|
| 1 | `Queued` | `Start` | `Resolving` |
| 2 | `Resolving` | `PlanReady` | `Downloading` |
| 3 | `Downloading` | `DownloadDone` | `Verifying` |
| 4 | `Verifying` | `VerifyPass` | `Installing` 或 `AwaitingElevation` |
| 5 | `Verifying` | `VerifyHardFail` | `Failed`（**且不可 `Cancelled` 后再继续**） |
| 6 | `AwaitingElevation` | `UacAccepted` | `Installing` |
| 7 | `AwaitingElevation` | `UacCancelled` | `Cancelled`（**不是 `Failed`**） |
| 8 | `Installing` | `InstallerExit0` | `Registering` |
| 9 | `Installing` | `InstallerExitNonZero` | `Failed` 或 `Partial` |
| 10 | `Installing` | `CancellationRequested` | 保持 `Installing`，置 `CancelRequested`（**不可立即中止**） |
| 11 | `Installing` | `Timeout` + 用户选择强制结束 | `Partial` |
| 12 | `Registering` | `RegistryFound` | `Done` |
| 13 | `Registering` | `RegistryNotFound` | `Partial`（安装器返回 0 但实际没装上） |
| 14 | `Failed` | `RollbackOk` | `RolledBack` |
| 15 | `Failed` | `RollbackImpossible` | `Partial` |
| 16 | `Queued` | `Cancel` | `Cancelled` |
| 17 | `Done` | 任意事件 | **抛 `InvalidOperationException`** |
| 18 | `Partial` | `UserMarkResolved` | `Partial`（保留，仅清标记） |
| 19 | `Installing` | `InstallerCrashed` | `Partial` |
| 20 | 任意终态 | `Cancel` | 幂等，无操作 |

> **第 17 条的意图**：终态后不允许再迁移。v0.2 曾出现「取消后又被进度回调推回 `Cancelled`」的隐患，必须在状态机层堵死。

### 2.5 摘要 JSON Schema 校验与降级 —— 15 条

| 场景 | 期望 |
|---|---|
| 合法完整 JSON | 反序列化成功，`Degraded=false` |
| 缺 `oneLiner` | 校验失败 → 丢弃 |
| `oneLiner` 超 180 字 | 校验失败 → 丢弃（不截断，因为截断后语义可能反转） |
| `keyFeatures` 超 10 项 | 校验失败 → 丢弃 |
| 多出未知字段 | **接受并忽略**（向前兼容） |
| `confidence` 非法值 | 校验失败 |
| JSON 前有 markdown 代码围栏 | 剥离后重试一次 |
| JSON 不完整（截断） | 丢弃，不重试 |
| 模型返回空字符串 | 触发离线模板降级 |
| 模型返回纯文本（非 JSON） | 丢弃 → 触发离线模板 |
| 字段含 HTML `<script>` | 校验通过但**渲染为纯文本**（§2.6 验证 UI 侧） |
| `installHint` 字段存在但为 null | 接受（可选字段） |
| 离线模板生成的摘要 | `Degraded=true`，字段齐全 |
| Token 计入超限 | 只记录，不影响校验 |
| 同一 `summaryKey` 二次生成 | 命中缓存，不调模型 |

### 2.8 运营白名单 —— 11 条

| 场景 | 期望 |
|---|---|
| 主体变更 + 白名单命中 + 签名有效 | `Proceed`，`TrustLevel.Whitelisted` |
| 主体变更 + 白名单命中 + 白名单签名无效 | **整体丢弃白名单** → `HardFail` |
| 主体变更 + 白名单未命中 | `HardFail` |
| 白名单 `whitelist_version` < 本地已见 | **拒绝加载**（防回滚） |
| 白名单 `whitelist_version` == 本地已见 | 接受 |
| 白名单文件缺失 | 视为空白名单 → 全部 `HardFail` |
| 白名单条目缺 `reviewedAt` | 拒绝该条 |
| 白名单条目缺少签名覆盖 | 拒绝该条 |
| 用户尝试「导入白名单」 | **不存在该功能**（编译期无 API） |
| 同一 `AppId` 有两条互斥的白名单记录 | 取 `reviewedAt` 最新，并记日志告警 |
| 白名单命中但哈希不匹配 | **仍 `HardFail`**（白名单只豁免主体一致性） |

### 2.9 子进程隔离（TH-11 / TH-12）—— 6 条

| 场景 | 期望 |
|---|---|
| 传给安装器的环境变量不含 Token | 断言 `ProcessStartInfo.Environment` 无敏感键 |
| 不使用 P/Invoke `CreateProcess` 自行传句柄 | 静态检查（R1） |
| `ArgumentList` 含空格/引号参数 | 实际拼出的命令行转义正确（§2.9b） |
| 安装器向 stdout 大量输出 | 不死锁（用假安装器输出 10 MB 验证） |
| 安装器不退出 | 超时机制触发，用户可放弃 |
| 父进程被强杀（真实安装器替身模拟不可安全终止） | 子进程不因 kill-on-close 被强杀；journal 保留，重启后状态进入 Unknown/Partial 并完成对账 |

### 2.10 D-13 复校（不信任调用方）—— 9 条

| # | 场景 | 期望 |
|---|---|---|
| D13-01 | **合法 `planId` 但对应校验结果为 `HardFail`** | **拒绝执行**（Lead 指定的核心用例） |
| D13-02 | `planId` 不存在 | 抛 `PlanNotFound` |
| D13-03 | `planId` 已执行过（幂等） | 返回缓存结果，不重复执行 |
| D13-04 | `planId` 对应的 `Capability` 已过期（`ProbedAt` 超 7 天） | 重新探测后再判定 |
| D13-05 | 调用方构造 `InstallPlan` 直接传（编译期不可能） | 接口只有 `planId` 参数，**编译期拒绝** |
| D13-06 | `ExecuteAsync` 的参数中不出现 `VerifyPolicy` | 签名断言（R2） |
| D13-07 | `planId` 对应的 `TargetDir` 在校验后被改 | 复校时重新走路径校验 |
| D13-08 | **取消后再调用 `ExecuteAsync`** | 拒绝（`Cancelled` 是终态） |
| D13-09 | 并发两个 `planId` | 串行化（`SemaphoreSlim`），第二个排队 |

> **D13-01 的意义**：这是把「红线无法被绕过」从口头承诺变成可执行断言的关键用例。v0.2 靠「恶意 UI 进程」论证它，v0.3 靠「防编码错误与未来重构」论证它。

### 2.11 `HardFail` 三个入口的约束（E-1..E-3）—— 8 条

| 场景 | 期望 |
|---|---|
| `HardFail` 时 UI 渲染的按钮集合 | **恰好** `{报告问题, 复制诊断, 查看详情}` |
| 三个命令的签名不含 `InstallPlan` / `AppId`+`InstallerId` 组合 | **编译期断言**（R3 分析器） |
| 复制诊断信息的字段 | 恰好 7 个字段，`sha256` 截断 16 位 |
| 复制诊断信息不含路径 | 正则断言无 `[A-Z]:\` 或 `\\\\` |
| 复制诊断信息不含机器名/用户名 | 断言无 `Environment.MachineName` / `UserName` 值 |
| 报告问题 URL | 只含 `appId` + `reasonCode`，无安装参数 |
| 不存在 URL scheme 激活路径 | 静态检查（无自定义协议注册） |
| 不存在命令行长参数触发安装 | 命令行解析器不接受安装类参数（R1） |

### 2.12 origin 判定（单向保守）—— 10 条

| 场景 | 期望 |
|---|---|
| 记录 + 哈希一致 + 路径一致 | `Origin.Store` |
| 记录 + 哈希一致 + 路径不同 | `Origin.Store` + `Drifted=true` |
| 记录在 + 注册表消失 + 目录在 | `Broken`，给「清理记录」 |
| 注册表有 + 无商店记录 | `Origin.External`（**不给更新/卸载**） |
| 用户手动装了更高版本 | `Origin.External` + 「是否接管？」（需确认） |
| `UninstallString` 指向不同目录 | `Origin.External` |
| 绿色安装有 `.githubstore.json` | `Origin.Store` |
| 绿色安装目录在但清单被删 | 「疑似残留」，**不自动删** |
| 指纹不一致但 `Origin.Store` | 卸载需二次确认 |
| 任意不确定情况 | **一律 `Origin.External`** |

### 2.13 JSON 软件源协议（docs/10）

| 场景 | 期望 |
|---|---|
| 有效官方源签名 | 验签成功且显示 `Official`；签名不替代安装包校验 |
| 第三方首次密钥 | 展示指纹并等待显式确认，不自动信任服务器同源公钥 |
| 未签名第三方源 | 可预览；添加和安装确认均有清晰警告 |
| 签名错误、源换钥或已验证源移除签名 | 拒绝新快照并暂停刷新，不降级为 `Unsigned`，继续旧缓存 |
| revision 小于最高已见值 | 按回滚攻击拒绝 |
| 同 revision 但原始字节/摘要变化 | 按篡改拒绝 |
| `index.json` 或任一详情未下载/摘要不符 | 不激活暂存快照；v1 必须先物化完整目录 |
| 导入事务中崩溃 | 重启后活动 revision 不变，暂存数据可清理 |
| 两源声明相同 `id` 与 `PackageId` | 生成不同 `SourceInstanceId`，目录记录互不覆盖 |
| 同仓库跨源版本不同 | 仅提示其他来源，不自动合并或换源 |
| 禁用/移除源 | 不删除 `install_records`，不触发卸载 |
| 已安装应用的原源不可用 | 更新状态为 Unknown/Unavailable，不从其他源自动更新 |
| JSON 含命令、PowerShell、hook 或未知安装器类型 | Schema 拒绝；执行层也无对应 API |
| 相对 URL | 仅相对最终 `source.json` URL解析，跨协议降级拒绝 |
| 重定向到 HTTP/私网、重定向超过 5 次 | 拒绝 |
| 超过下载、解压、深度、条数或字符串限制 | 流式终止并清理临时文件，旧快照可用 |
| 源签名有效但资产哈希/Authenticode 失败 | 安装仍按 `VerifyPolicy` 阻止 |

性能基准至少覆盖 500、5,000、20,000 条三档，记录下载大小、解析耗时、SQLite 事务耗时和进程峰值 WS。完整限制与验收清单见 docs/10 §10/§12。

## 3. 服务接口契约测试（原「跨进程契约」的替代）

### 3.1 为什么还需要

单进程后没有跨语言契约，但**仍有契约**：UI 开发者会用 fake 实现（`ICatalogService`/`IInstallService`）来开发界面。如果 fake 的行为与真实实现不一致，UI 就会在集成时才暴雷。

**风险场景**：fake 的 `ProbeAsync` 永远返回「支持自定义路径」，真实实现在某些包上返回「不支持」。UI 开发时一切正常，联调时大量路径置灰逻辑没写。

### 3.2 做法

```csharp
// 同一套用例，跑两遍：一次真实实现（内存 SQLite + 假 HTTP），一次 fake 实现
public abstract class InstallServiceContractTests
{
    protected abstract IInstallService CreateService();

    [Fact]
    public async Task ProbeAsync_ReturnsCapabilityWithProbedAt()
    {
        var svc = CreateService();
        var cap = await svc.ProbeAsync(TestData.AppWithMsi, TestData.FetchOptions);
        cap.ProbedAt.Should().BeAfter(DateTimeOffset.UtcNow.AddMinutes(-1));
        cap.AppId.Should().Be(TestData.AppWithMsi);
    }

    // ... 每个服务方法 2–4 条契约
}

public sealed class RealInstallServiceTests : InstallServiceContractTests
{
    protected override IInstallService CreateService() => /* 真实实现 + 内存库 */;
}

public sealed class FakeInstallServiceTests : InstallServiceContractTests
{
    protected override IInstallService CreateService() => /* 测试用 fake */;
}
```

### 3.3 契约测试矩阵

| 服务 | 契约条目 | 说明 |
|---|---|---|
| `ICatalogService` | 8 | 分页边界、空结果、`HasMore` 正确性、分类不存在 |
| `ISearchService` | 6 | 空查询、远程失败时 `RemoteError` 非抛、`Source` 取值 |
| `IInstallService` | 12 | `PlanAsync` 无副作用、`ExecuteAsync` 复校、取消语义 |
| `IInventoryService` | 8 | 三态判定、更新检查、卸载幂等 |
| `ISummaryService` | 6 | 缓存命中、`IProgress` 报告次数、取消传播 |

### 3.4 门禁

- 任一服务接口变更 → 契约测试必须同步更新；CI 检查「接口签名 hash 变化但契约测试未变」→ 失败。
- fake 实现必须与真实实现通过**同一套**契约测试（这是本节的全部价值）。

## 4. 集成测试

### 4.1 假安装器（替代真实第三方包）

`tests/fixtures/fake-installer/` 下的自写 exe（或 C# 脚本），通过参数控制行为：

| 参数 | 行为 |
|---|---|
| `--succeed` | 建目录 + 写注册表 + 返回 0 |
| `--fail=<code>` | 返回指定非 0 |
| `--hang` | 不退出（测超时） |
| `--no-output` | 不输出任何内容（测进度推断） |
| `--flood-output` | 输出 10 MB（测 stdout 死锁） |
| `--write-registry=<path>` | 写指定注册表（测注册表校验） |
| `--ignore-location` | 忽略传入目录，装到别处（测「事后校验」） |
| `--crash` | 立即崩溃（测 `Partial`） |
| `--sleep=<ms>` | 模拟慢安装（测进度与取消） |

> **收益**：可覆盖全部状态机路径，且**完全确定性**。真实包只在发布前手工抽检。

### 4.2 `IProcessRunner` 假实现

```csharp
public sealed class FakeProcessRunner : IProcessRunner
{
    public List<ProcessInvocation> Invocations { get; } = [];
    public Queue<ProcessOutcome> Outcomes { get; } = new();

    public Task<ProcessResult> RunAsync(ProcessRequest req, IProgress<string>? output,
                                        CancellationToken ct)
    {
        Invocations.Add(new(req.FileName, req.Args, req.RequiresElevation));
        return Task.FromResult(Outcomes.Dequeue().ToResult());
    }
}
```

**用途**：断言「是否带 `runas`」「参数是否被正确转义」「无签名文件是否被拒绝提权」——**不需要真的弹 UAC**。

### 4.3 进程级测试

| 测什么 | 方法 | 断言 |
|---|---|---|
| 冷启动到可交互 | 启动 exe，ETW 或 UI 打点 | ≤3.0 s P95 |
| 托盘隐藏后内存回落 | 启动 → 导航列表 → 关窗 → 等待 → 采样 | WS ≤110 MB |
| 反复开关窗口 20 次 | 循环 + 采样句柄/内存 | 无线性增长 |
| 崩溃后 journal 恢复 | 安装中途 `Kill` 主进程 → 重启 | 检测到未完成事务，状态正确 |
| 安装器挂起 | 假安装器 `--hang` | 超时触发，UI 不卡死 |
| 父进程被杀时子进程回收 | 启动 `--hang` 安装器 → `Kill` 主进程 | 安装器进程消失 |

### 4.4 提权路径怎么测

**CI 无法自动化 UAC**（`runas` 必然弹窗，且无法在无头环境响应）。因此：

| 层 | 手段 |
|---|---|
| 单元 | `FakeProcessRunner` 断言「请求了 `runas`」+「参数正确」 |
| 单元 | 断言「无签名文件 + `RequireElevation` → 抛 `elevate.requires_signed_binary`」 |
| 手动 | 专用测试机上真实走一遍，检查 UAC 弹窗显示的是**安装器名**而非我们的程序名 |
| 手动 | UAC 点「否」→ 断言状态为 `Cancelled` 而非 `Failed` |

**v0.3 说明**：v0.2 有「假提权执行器（跨语言）」测试，v0.3 改为上面第 1、2 条的 `FakeProcessRunner` 方案——更简单，覆盖同样的逻辑分支。

### 4.5 测试机与快照策略

| 层 | 环境 |
|---|---|
| L0–L2 | CI runner（Windows Server 2022 + Windows App SDK） |
| L3 | Windows 11 24H2 VM，每次测试前回滚快照 |
| L4 | 真实机器：Win11 x64、Win10 22H2、Win11 arm64 各一台 |

### 6.2 怎么测（协议）

| 项 | 规定 |
|---|---|
| 机器 | 固定测试机，关闭其它应用，接通电源（高性能模式） |
| 采样 | 1 s 间隔，5 min 稳态，取 P95 |
| 次数 | 每项 ≥3 次，取中位数 |
| 预热 | 冷启动测试前重启机器；热启动测试前先启动一次再退出 |
| 报告 | 必须同时报告 WS 与 PM，**不混用** |

**PowerShell 采样脚本（单进程口径）**：

```powershell
param([string]$Name = 'githubstore-ui', [int]$Seconds = 300)
$samples = for ($i = 0; $i -lt $Seconds; $i++) {
    $p = Get-Process -Name $Name -ErrorAction SilentlyContinue
    if ($p) {
        [pscustomobject]@{
            WS_MB   = [math]::Round($p.WorkingSet64 / 1MB, 1)
            PM_MB   = [math]::Round($p.PrivateMemorySize64 / 1MB, 1)
            Handles = $p.HandleCount
            Threads = $p.Threads.Count
        }
    }
    Start-Sleep -Seconds 1
}
$samples | Measure-Object WS_MB, PM_MB, Handles, Threads -Maximum -Average |
    Sort-Object Property | Format-Table -AutoSize

# 安装器子进程单独记录（不计入 NFR）
Get-Process -Name 'msiexec','MsiExec','setup','*install*' -ErrorAction SilentlyContinue |
    Select-Object ProcessName, @{n='WS_MB';e={[math]::Round($_.WorkingSet64/1MB,1)}}
```

## 9. 红线验收口径：「不存在忽略校验开关」如何被自动验证

> **本节是 docs/07 §11.2 治理条款的技术落地。** 四道门禁必须全绿——只做 R1 会漏掉后三种（它们都能在不出现敏感标识符的情况下实现）。

### 9.1 R1：标识符 grep 门禁

扫描 `src/**/*.cs`（排除 `*.Tests.cs` 与 `tests/**`），命中即失败，**无 override**：

| 模式 | 拦截原因 |
|---|---|
| `skipVerify` / `SkipVerify` / `skip_verify` | 跳过校验 |
| `ignoreSignature` / `IgnoreSignature` | 忽略签名 |
| `insecure` / `Insecure` / `DangerousAcceptAny` | 不安全开关 |
| `RemoteCertificateValidationCallback` 赋值为恒 `true` | TLS 绕过 |
| `--force` / `force-install` / `ForceInstall` | 强制安装 |
| `bypass` / `Bypass` | 绕过 |
| `trustAll` / `AlwaysValid` | 信任一切 |

```powershell
$bad = @('skipVerify','SkipVerify','skip_verify','ignoreSignature','IgnoreSignature',
         'insecure','Insecure','ForceInstall','force-install','Bypass','bypass',
         'trustAll','AlwaysValid')
$files = Get-ChildItem src -Recurse -Filter *.cs |
         Where-Object { $_.Name -notlike '*.Tests.cs' }
$hits = $files | Select-String -Pattern $bad
if ($hits) { $hits | ForEach-Object { Write-Error "$($_.Path):$($_.LineNumber)" }; exit 1 }
```

### 9.3 R3：Roslyn `DiagnosticAnalyzer`

**目标**：`VerifyPolicy.HardFail` 分支下不允许出现任何「执行安装」的调用或「继续」控件。

```csharp
[DiagnosticAnalyzer(LanguageNames.CSharp)]
public sealed class HardFailNoContinueAnalyzer : DiagnosticAnalyzer
{
    private static readonly DiagnosticDescriptor Rule = new(
        id: "GS0001",
        title: "HardFail 分支不得出现继续安装的路径",
        messageFormat: "在 VerifyPolicy.HardFail 分支中发现 '{0}'，违反红线（docs/07 §4.3）",
        category: "Security",
        defaultSeverity: DiagnosticSeverity.Error,
        isEnabledByDefault: true);

    public override ImmutableArray<DiagnosticDescriptor> SupportedDiagnostics => [Rule];

    public override void Initialize(AnalysisContext ctx) =>
        ctx.RegisterSyntaxNodeAction(AnalyzeSwitchSection, SyntaxKind.SwitchSection);

    private void AnalyzeSwitchSection(SyntaxNodeAnalysisContext ctx)
    {
        // 1) 定位 case VerifyPolicy.HardFail:
        // 2) 遍历该 section 的所有 InvocationExpression / ObjectCreation
        // 3) 若出现 ProcessRunner.Run / Process.Start / Button.Visibility=Visible / RelayCommand.Execute
        //    → ReportDiagnostic
    }
}
```

**实现要点**：
- 用 `RegisterSyntaxNodeAction(SyntaxKind.SwitchSection)` 而非遍历全树，性能好且定位准。
- 需要同时覆盖 `if (policy == VerifyPolicy.HardFail)` 这种写法 → 额外注册 `SyntaxKind.IfStatement`。
- **分析器自身也需要测试**（TBD-08-13）：用 `Microsoft.CodeAnalysis.Testing` 的 `CSharpAnalyzerVerifier` 注入违规代码，断言能报错。

### 9.4 R4：调用图不可达性

**目标**：从 `HardFail` 分支出发，不存在到 `IInstallService.ExecuteAsync` 的调用路径。

| 实现方式 | 取舍 |
|---|---|
| Roslyn `Compilation` + 手写调用图遍历 | 准确，但对 async/委托/反射有限 |
| 简化为「grep 反向 + code review checklist」 | 成本低，但漏反射与委托 |
| **推荐**：Roslyn 编译期构建 + 已知限制清单 | 接受「反射/委托不可检测」这一局限，用 code review 兜底 |

**已知局限（必须写在文档里）**：
- 通过 `Func<...>` 委托或反射调用无法被静态分析捕获。
- 因此 R4 **不能替代 code review**，只能减少明显错误的概率。

### 9.5 检查结果与处置

| 结果 | 处置 |
|---|---|

### 补充：单进程架构专属测试点（v0.3 新增）

> 单进程带来的新风险不在「功能对不对」，而在「进程会不会卡死/泄漏」。以下四类必须覆盖，已在 §4.3 与 §6 中体现。

| # | 风险 | 测试手段 |
|---|---|---|
| 1 | **UI 线程被阻塞** | ① VSTHRD 分析器编译期拦截；② B-13 响应性探针（安装期间随机测量 UI 输入到响应的时间）；③ L3 集成测试中并发发起安装 + 滚动列表，断言帧率不下降 |
| 2 | **`async void` 异常被吞** | 单测订阅 `AppDomain.CurrentDomain.UnhandledException` 与 `TaskScheduler.UnobservedTaskException`，注入抛异常的 `async void` 处理器，断言**全局处理器被调用**（而不是进程静默继续） |
| 3 | **后台任务取消不传播** | 取消安装后断言：`CancellationToken` 已置位、子进程已被终止、`CancellationException` 被正确上报、journal 记录 `Cancelled` |
| 4 | **ViewModel 事件订阅泄漏** | 反复导航进出详情页 100 次 → `GC.Collect()` → 断言存活的 ViewModel 实例数不增长（弱引用计数）；这是 §4.3 的 TBD-04-9 |
