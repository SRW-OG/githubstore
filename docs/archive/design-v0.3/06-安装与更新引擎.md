# 06 · 安装与更新引擎

> 本章定义 GitHubStore 的安装 / 更新 / 卸载引擎：从「用户点安装」到「软件可用」的完整路径——来源适配、包类型识别、下载与校验、路径策略、事务与提权、已安装对账、卸载与错误文案。
> **v0.3 变更（2026-10-18）**：架构改为**单进程 C#**（删除 Go）。① 全部模块改为 C#（`Process` / `SemaphoreSlim` / `CancellationToken` / `IncrementalHash`）；② **提权方案重写**——v0.2 的独立 Go 提权进程 `gs-elevate.exe` + 白名单动作 + HMAC plan **全部移除**，改为 `Process.Start` + `Verb="runas"` 直启安装器；③ 新增子进程防御（超时/心跳/Job Object/stdout 死锁）；④ §10 TBD 与 §11 风险同步改写。
> **确定性声明**：本章在无外网沙箱中撰写，**没有任何一条外部事实经过本机验证**（HTTPS 出站被拦，winget 亦无法执行）。凡涉及 winget 行为、退出码数值、安装器参数、Windows API 语义者，只标 `[文档]`（有官方文档/头文件依据）或 `[待验证]`（社区经验或推理）。本章**不存在「已验证」级条目**，实现前必须按 §10 逐条落地。

## 本章结论（TL;DR）

1. **winget 只当「解析器 + 兜底安装器」，不当唯一通路**（ADR-002）：主路径是 `winget` CLI 子进程 + 结构化解析，同时冻结 COM 适配器接口备用。
2. **`--location` 不是通用能力**（ADR-004）：仅当 manifest 声明 `InstallerSwitches.InstallLocation` 才真正传给安装器；MSIX / Squirrel / 多数未声明的 NSIS·Inno 会**静默忽略**。故「自定义路径」= **尝试 → 事后校验真实 InstallLocation → 回退**，绝不信任参数返回值。
3. **三策略并存 `Default` / `Custom` / `Green`**，默认 `Default`；`Green`（解压即用、不写注册表、删目录即卸载）是差异化能力，但只对 ZIP/7z/portable 成立，其余类型必须置灰并给出降级文案。
4. **一次安装 = 一个可恢复事务**：SQLite `journal` 表逐条写入并提交，崩溃后按状态重放；整个事务**最多一次 UAC**。
5. **提权方式（v0.3 重写）**：主程序**永不整体提权**，需要时用 `Verb="runas"` **直接启动安装器本体**。代价是：提权后拿不到安装器的 stdout/进度，且无法约束安装器做什么。**前置硬规则：只有通过完整校验链（哈希 + 签名）的文件才允许 `runas`。**
6. **只有 `Origin.Store` 才给「更新 / 卸载」按钮**：origin 由 `(AppId, installerSha256, installPath)` 指纹证据链判定，其中 `AppId = SourceInstanceId + PackageId`；用户自装软件一律只读展示 + 「去官网」。
7. **默认极省资源**：单连接流式落盘（>32 MiB 才可选分段）、安装并发恒为 1、已安装扫描惰性 + 60 s 缓存、注册表扫描走低优先级任务。
8. **安装器子进程必须被防御性等待**（v0.3 新增）：超时/取消只停止等待并把任务标为 `Partial/Unknown`，随后通过注册表、MSI/MSIX 状态和绿色清单对账；不得把真实安装器放进 `KILL_ON_JOB_CLOSE` Job Object。只有商店自有、确认可终止的辅助进程或测试替身才允许随宿主回收。

## 0. 章节定位、术语与对外接口

模块划分：`M-06-1` 来源适配层（全仓唯一允许调用 winget 处）｜`M-06-2` 包类型识别器｜`M-06-3` 下载器｜`M-06-4` 校验器｜`M-06-5` 事务引擎｜`M-06-6` **子进程执行器 `IProcessRunner`**（v0.3 重定义，见 §6）｜`M-06-7` 清单与对账｜`M-06-8` 卸载器。**全部模块跑在同一个 `githubstore-ui.exe` 进程内**（v0.3 无独立提权进程）。

术语对齐 docs/01：`AppId`（`SourceInstanceId + PackageId` 的复合身份）、`InstallPlan`（不可变安装计划，`record` + `init`）、`InstallRecord`（已安装事实，含 `Origin`）、`UpdateInfo`（可用更新）、`Capability`（能力事实）、`VerifyPolicy`（校验裁决）。
本章新增提案：`FR-06-1` 三策略安装、`FR-06-2` 单次 UAC、`FR-06-3` origin 门控、`FR-06-4` 断点续传、`FR-06-5` 卸载残留提示；`NFR-06-1` 引擎内存增量 ≤20 MiB（单进程口径下的增量，非独立进程）、`NFR-06-2` 下载内存恒定（不随文件增长）。

## 1. 安装资产通道与包类型

### 1.1 来源枚举

| `SourceKind` | 触发场景 | 资产获取方式 | 备注 |
|---|---|---|---|
| `winget` | 用户选「winget 安装」 | `winget show --id <Id> -e` 解析 Installer Url/Type，或整体交给 winget | 依赖系统 App Installer |
| `github` | 默认：Release 资产直下 | `/repos/{o}/{r}/releases` 的 `assets[]` | 本章主战场，见 §3 |
| `local` | 用户拖入本地 `.exe/.msi/.zip` | 文件系统 | 离线 / 内测 / 复现 bug |

**这里的 `SourceKind` 是“安装资产获取通道”，不是 docs/10 的“目录软件源订阅”。** 一个自定义 JSON 源可以为条目声明 GitHub 直下或 winget 通道；不论通道如何，安装记录都必须保留原 `SourceInstanceId`。

**结论**：资产通道只影响「资产怎么拿到」，识别、策略、事务、卸载四层必须对三个通道完全一致，否则会出现「winget 装的能卸载、直下的不能」这类产品级割裂。

### 1.2 包类型分类

| `PackageType` | 判据（强 → 弱） | 静默 | 自定义路径 | 可回滚 |
|---|---|---|---|---|
| `msi` | 魔数 `D0CF11E0A1B11AE1`（OLE）；`MsiOpenDatabase` 可读 Property 表 | ✅ `/qn` | ⚠️ 视包内属性 | ✅ MSI 自带 |
| `msix`/`appx` | ZIP 魔数 `504B0304` 且内含 `AppxManifest.xml` | ✅ | ❌ | ❌ 仅移除 |
| `exe-nsis` | 字符串 `Nullsoft Install System` / `Nullsoft.NSIS` | ✅ `/S` | ✅ `/D=` | ❌ |
| `exe-inno` | 字符串 `Inno Setup Setup Data` / `Inno Setup` | ✅ `/VERYSILENT` | ✅ `/DIR=` | ⚠️ 部分 |
| `exe-squirrel` | `Update.exe`、`RELEASES`、`app-<ver>\`、`*.nupkg` | ✅ `--silent` | ❌ | ❌ 只能重装旧版 |
| `exe-installshield` | 字符串 `InstallShield`、`_setup.dll`、`ISSetupStream` | ✅ `/s` | ⚠️ 仅 Basic MSI | ❌ |
| `exe-wixburn` | `wixburn` / `.wixburn` 节 / `wixstdba.dll` | ✅ `/quiet` | ⚠️ 仅声明变量 | ⚠️ 部分 |
| `archive`（zip/7z） | `504B0304` / `377ABCAF271C` | 不适用 | ✅ 即解压目录 | ✅ 删目录 |
| `portable-exe` | 单 PE、无安装器特征、无卸载注册表项 | 不适用 | ✅ 复制 | ✅ |
| `script` | `.ps1/.cmd/.bat` | ❌ 需确认 | ✅ | ❌ |
| `unknown` | 以上皆不匹配，置信度 < 阈值 | ❌ 交互 | ❌ | ❌ |

**结论**：**「支持自定义路径」是包类型的属性，不是用户偏好**——UI 必须在展示选项时就按本表置灰，而不是装完再道歉。

### 1.3 识别流水线（四级降级）与误判兜底

1. **扩展名**（`.msi/.msix/.msixbundle/.appx/.exe/.zip/.7z`）：最廉价，只用于分流。
2. **魔数**（前 8 字节）：OLE → MSI；`PK\x03\x04` → 先当 ZIP，再看内部有无 `AppxManifest.xml`（MSIX）或 `*.nuspec`+`RELEASES`（Squirrel）；7z 魔数 → archive。
3. **PE 版本信息**：由 `Platform.Win32` 用 C# P/Invoke 调 `GetFileVersionInfoSizeW` → `GetFileVersionInfoW` → `VerQueryValueW("\\StringFileInfo\\<lang><cp>\\")` 读 `CompanyName/ProductName/FileDescription/OriginalFilename`。
4. **字节串特征扫描**：1 MiB 窗口流式扫 NSIS/Inno/Squirrel/InstallShield/WiX 特征串，命中即定级；扫描上限 8 MiB，避免大文件拖慢首屏。辅助信号（不作唯一判据）：资产命名（`*-setup.exe`、`*-x64.msi`）、`*.nuspec` 的 `packageTypes`、Release body 的安装说明。

| 误判情况 | 兜底 |
|---|---|
| 多特征冲突（如 Inno 包内嵌 MSI） | 取「最外层安装器」类型，另一个记 `nestedType`，静默参数以外层为准 |
| 判为 `exe-*` 但静默启动 5 s 内无子进程且无窗口变化 | 降级为**交互安装**：起 GUI 由用户点完，引擎只负责事后检测（§7） |
| 完全无法识别（自研安装器） | `PackageType=unknown` + `confidence=low`，禁用 `custom/green`，只允许默认路径 + 交互安装 |
| 置信度低于阈值 | 安装前弹一次「无法确定安装器类型，将以交互方式运行」，判定写入 journal 便于复现 |

**结论**：识别器**不允许「低置信度 + 静默安装」组合**——错误类型配上静默参数，等于在用户机器上无人值守地搞破坏。

**交互式安装的窗口行为（WinUI 3）**：降级为交互安装时，Core 先请求 UI 把商店主窗口**最小化**（不是隐藏到托盘，便于用户找回），再启动安装器并把其窗口置前；安装器退出后 Core 发事件让 UI **恢复原窗口与焦点**。商店**不得覆盖安装器的置顶行为**（不抢 Topmost、不抢前台），否则用户点不到安装器的「下一步」。

**Core 无窗口进程的前台授权（关键补丁）**：Core 本身没有窗口，Windows 前台激活规则会阻止它把前台让给安装器，故 Core 须以 `SW_SHOWNORMAL` 启动安装器，并**在启动前后调用 `AllowSetForegroundWindow(pid)`** 显式授权安装器抢占前台。若安装器启动后 **5 秒内未出现可见窗口**（用 `GetForegroundWindow` + `EnumWindows` 按 PID 粗判，辅以 `IsWindowVisible`），UI 显示提示「**安装程序可能需要你在任务栏中切换窗口**」，避免用户在 Core 无窗口的场景下误以为卡死。`[待验证]`：该 5 秒阈值与 `EnumWindows` 判定在 UAC 提升型安装器（子进程 PID 与父进程不同）上的可靠性——提权后 PID 会变，需按进程树而非单 PID 匹配。

## 2. winget 集成（ADR-002）

### 2.1 三种方案对比

| 维度 | CLI 子进程 | COM API `Microsoft.Management.Deployment` | 直读 winget 源清单 |
|---|---|---|---|
| 可控性 | 高：任意参数、可 kill、可设环境 | 中：仅 IDL 属性，`InstallOptions` 受版本约束 | 高：全自己算，等于重写 winget |
| 进度粒度 | 低：仅日志/控制台，无结构化事件 | 中高：`InstallProgress` 回调有 state/percent | 高：下载进度自己实现 |
| 自定义安装路径 | 有 `--location`（受 manifest 限制，§2.4） | **疑似无等价属性** `[待验证]` | 最强：自己传参 |
| 对用户配置影响 | 写 winget pin/settings/源缓存 | 同左 | 无（只读源） |
| 依赖与部署 | 需系统已装 App Installer（Win11 预装） | 同左 + WinRT 激活（unpackaged 调用有坑） | 需自建源索引/解析 YAML，成本最高 |
| 错误可诊断性 | 高：stderr + 退出码 + `--log` | 中：只有 HRESULT | 高：全是自己的码 |
| 许可证/再分发 | winget-cli 为 MIT `[文档]`；「App Installer」随应用捆绑需法务确认 `[待验证]` | 同左 | 源清单为公开数据，源服务条款另论 |

**结论**：CLI 是唯一能在「自定义路径 + 原始错误」两个维度同时达标的形态，实现成本也最低；COM 的进度优势不足以抵消 `--location` 缺口与 WinRT 激活风险。

### 2.2 决策 ADR-002

> **采用「CLI 子进程为主 + 结构化输出解析 + COM 适配器接口预留」。**

定义窄接口 `WingetBackend`，两实现：`cliBackend`（v1 唯一）、`comBackend`（v2 候选，接口先冻结、实现留空）。所有 winget 交互**必须**经 `M-06-1`。winget 不可用（未安装 / `0x8A15xxxx` 级错误 / 被策略禁用）时，不静默换通道；只有同一活动快照同时声明经验证的 HTTP 安装器时，商店页才可提供“改用直下”，重新生成并展示安装计划，用户确认后冻结新的 channel/URL/hash。更新阶段同样不得绕过原绑定自动切换。

### 2.3 参数矩阵

基线：`winget install --id <Id> -e --source winget --accept-package-agreements --accept-source-agreements --silent --scope user|machine --location "<dir>" --override "<args>" --disable-interactivity --log "<file>"`

| 参数 | 能做什么 | 不能做什么 | 副作用 |
|---|---|---|---|
| `--id` + `-e` | 精确匹配标识符，避开模糊名歧义 | 包下架/改 ID 即失败 | 无 |
| `--source winget` | 锁定官方源，避免 msstore 源弹 Store 协议 | 装不了第三方源包 | 首次可能触发源更新（联网） |
| `--accept-package-agreements` / `--accept-source-agreements` | 跳过协议确认（无人值守必需） | 不代表用户已读协议，UI 仍须呈现 | 无 |
| `--silent` | 请求安装器静默 | **不是保证**：manifest 未声明 `InstallerSwitches.Silent` 时可能仍弹窗 | 静默失败无提示，用户以为卡住 |
| `--scope user\|machine` | 指定安装范围，`user` 免 UAC | **包不一定支持该 scope**，winget 会回退或报错 | machine 需提权；scope 与 `--location` 可能互斥 |
| `--location <dir>` | 传给支持自定义路径的安装器 | 见 §2.4，多数包不生效 | 目录会被创建；不生效时留空目录 |
| `--override "<args>"` | 完全替换 winget 生成的安装参数 | 覆盖后 winget 不再注入静默/日志参数，**责任全在调用方** | 拼错即让安装器进交互模式并挂起 |
| `--disable-interactivity` | 禁止一切交互提示（协议、源更新确认） | 不保证安装器自身不弹窗 | 必须与 `--accept-*` 成对，否则可能卡在提示 |
| `--log <file>` | 落全量日志供解析/排障 | 无结构化 schema，格式随版本变 | verbose 时体积可观 |

**结论**：`--silent` / `--scope` / `--location` 三者都是「**请求**」而非「**保证**」，引擎必须假设它们被忽略，一律以事后检测为准。

**进度采集**：winget **没有结构化进度事件**，CLI 仅在 TTY 下渲染进度条，重定向后输出会简化 `[待验证]`。故 v1 以 `--log` tail 解析为主手段（跟 `Downloading`/`Installing`/`Successfully installed` 关键字映射到 0/33/66/100 四档），辅以监视 `%TEMP%\WinGet\**` 体积增长（路径名 `[待验证]`，仅在已知 `Content-Length` 时合成百分比）；`--disable-interactivity` 会关掉交互提示，但**对进度输出的影响 `[待验证]`**，非 TTY 下可能完全无进度。**只承诺阶段级进度，不承诺百分比**——UI 用不确定进度条 + 阶段文案，避免「卡在 47%」的信任崩塌；COM 的 `InstallProgress` 作为 v2 提升精度的理由记录在 ADR-002。

**进度上报链路（v0.3）**：`InstallService → IProgress<InstallProgress> → ViewModel`。服务层先对进度做**合并节流（≤20 次/秒，同一阶段内只保留最新值，阶段切换立即 flush）**再 `Report`，`Progress<T>` 自动 marshal 回 UI 线程；UI 侧**只做渲染**，不参与进度计算与状态判定。节流的原因不再是「省管道带宽」，而是**保护 `DispatcherQueue` 的每帧预算**——每个 token 都触发一次 UI 更新会让界面比「一次性返回」更卡。

### 2.4 `--location` 的真实限制（本章最容易踩的坑）

**机制**：winget 仅在 manifest 的 `InstallerSwitches` 声明了 `InstallLocation`（含 `<INSTALLPATH>` 占位符）时，才把 `--location` 格式化进安装器命令行 `[文档]`；未声明时 winget **不报错、直接忽略**，部分版本对 `msix`/`squirrel` 直接拒绝 `[待验证]`。

| 包类型 | `--location` 行为 | 等级 |
|---|---|---|
| MSI | 有声明才传属性（常见 `TARGETDIR`/`INSTALLDIR`）；属性名由作者定，不尊重则无效 | `[文档]`+`[待验证]` |
| MSIX/APPX、Squirrel | 无效。分别固定 `C:\Program Files\WindowsApps` 与 `%LOCALAPPDATA%\<AppName>` | `[文档]` |
| NSIS / Inno | 有声明时走 `/D=` / `/DIR=`，未声明则忽略 | `[待验证]` |
| `portable` / `zip`（winget 1.6+ 原生解压类型） | 有效，指向落地目录 | `[待验证]` |

**「尝试 → 检测 → 回退」流程（必须按此实现）**：

1. **预判**：`winget show --id <Id> -e` 解析 `Installer Type`；`msix/appx/squirrel` → 直接判定不支持，UI 置灰（不等装完）。
2. **尝试**：加 `--location` 执行，同时记录请求目录。
3. **检测（关键）**：装成功后**不信任参数**，扫注册表 Uninstall 项取该包 `InstallLocation` 与请求目录比对：等于 → `custom` 成功；不同 → **降级为 default**，写实际路径并提示「该安装包不支持自定义路径，已安装到 `<实际>`」；无字段 → 按 `DisplayIcon`/`UninstallString` 反推，仍失败记 `path=unknown`。
4. **回退（产品级）**：用户强需自定义路径且当前为 winget → 只有活动快照还声明合适的 HTTP `exe-*` 安装器时，才显示“改用直下”；重新生成计划并让用户确认新通道、URL、哈希和权限，不自动切换。
5. **清理**：不生效时删除因 `--location` 预创建的空目录。

**scope 与提权**：`user` 免 UAC，落地 `%LOCALAPPDATA%\<App>`，但包可能不支持（→ 报错或回退 machine `[待验证]`）；`machine` 需提权，落地 `C:\Program Files\<App>`，未提权报 `0x80070005`、策略禁用报 `1625`。默认策略：**先试 `user`，仅在错误属于「scope 不支持」时才请求一次 `machine` + 提权**；绝不先提权再回退 user（多弹一次 UAC，违反 `FR-06-2`）。

**结论**：把 `--location` 当「尽力而为的提示」，把**注册表实际 `InstallLocation`** 当唯一真相；UI 文案绝不能承诺「装到 D:\Apps」。

### 2.5 退出码映射

解码算法：`uint32` 按高 16 位分流——`0x8007xxxx` 属 `FACILITY_WIN32`，用 `HRESULT_FROM_WIN32` 反解；`0x8A15xxxx` 属 winget CLI 私有域，**必须查表**。

| 退出码 | 用户可读原因 | 建议动作 | 可重试 | 等级 |
|---|---|---|---|---|
| `0` | 成功 | 进入 §7 对账 | — | `[文档]` |
| `3010` | 安装完成，需重启生效 | 提示重启，记 `needsReboot` | ❌ | `[文档]` |
| `1602`/`0x80070642` | 安装被取消 | 允许重试 | ✅ | `[文档]` |
| `1603`/`0x80070643` | 安装程序内部错误 | 收集 `--log`，引导看日志/联系开发者 | 有限 | `[文档]` |
| `1618`/`0x80070652` | 有别的安装正在进行 | 提示稍后重试；引擎侧排队 | ✅ | `[文档]` |
| `1619`/`1620` | 安装包损坏或无法打开 | 重新下载并校验 | ✅ | `[文档]` |
| `1625` | 系统策略禁止安装 | 提示联系管理员 | ❌ | `[文档]` |
| `1633` / `1638` | 该包不支持当前系统/架构 / 已存在其他版本 | 换资产（arm64/x64）或提示先升级 | ❌ | `[文档]` |
| `0x80070005` / `0x80070070` | 需要管理员权限 / 磁盘空间不足 | 走提权路径，或清理后重试 | ✅ | `[文档]` |
| `0x800704C7` | 你取消了管理员授权 | 降级用户级/绿色安装 | ✅ | `[文档]` |
| `0x800B0109` | 安装包签名不受信任（常见 MSIX） | 拒绝安装并提示来源 | ❌ | `[待验证]` |
| `0x80073CF3`/`0x80073CFB` | MSIX 依赖缺失 / 版本冲突 | 提示更新系统组件 | 有限 | `[待验证]` |
| `0x8A150001`…`0x8A1500FF` | winget 自身错误域（参数错、找不到包、哈希不匹配、位置不支持…） | 依子码；**未知子码**统一「winget 报错，附原始码」 | 视子码 | `[待验证]` |

**实现纪律**：`0x8A15xxxx` 表**不得凭记忆手写**，须从 `microsoft/winget-cli` 的 `AppInstallerErrors.h` 生成 `errors_generated.go`；表外码落 `ErrWingetUnknown` 并原样展示十六进制。上表私有域**具体数值未逐个核对**，故整段标 `[待验证]`。

**结论**：`0x8007xxxx` 段可精确反解、文案可靠；`0x8A15xxxx` 段必须代码生成 + 未知码兜底——「凭印象写的退出码表」是 bug 温床。

## 3. HTTP 直下 GitHub Release

### 3.1 资产选择规则

按序过滤（全在内存中对 `assets[]` 计算，零额外网络）：

1. **排除**：`*.sha256/*.sha256sum/*checksums*/*.sig/*.pem/*.asc/*.sbom*/*.spdx*/*.pdb/*.symbols*/*source*/*src.zip`、`*.json` 清单、`*.txt` 说明。
2. **平台**：命中 `windows|win32|win64|win-` 优先；命中 `linux|darwin|macos|osx|freebsd|android` 排除。
3. **架构**：`arm64|aarch64`（arm64 机）> `x86_64|amd64|x64|win64`（x64 机）> `386|i386|x86|win32`（兜底）；两者同现时按 `runtime.GOARCH` 加权。
4. **安装器关键字**：`setup|installer|install|full` > `portable|standalone` > 无后缀。
5. **类型偏好**：`green` 策略下 `zip/7z` 优先；`default/custom` 下 `msi/msix/exe` 优先。
6. **兜底**：过滤后为空 → 全部资产按体积降序取第一个可执行，UI 标注「自动选择，可能不是你要的版本」。

**API 取舍**：列表用 `api.github.com`（有 `assets[].digest/size/content_type`，便于精确选择）；下载走 `browser_download_url`（重定向 CDN，**不消耗 API 配额**）。Token 只加在 `api.github.com` 上，**绝不发给 `objects.githubusercontent.com`**（安全红线，见 docs/07）。

**结论**：资产选择必须「规则化 + 可解释」——命中哪条规则要能回显给用户，否则「为什么下成了 ARM 版」永远说不清。

### 3.2 下载引擎与校验链

| 能力 | 设计 | 依据 |
|---|---|---|
| 单连接 vs 分段 | 默认单连接；`size > 32 MiB` 且 `Accept-Ranges: bytes` 时才**可选** 4 段 `[待验证]` | 少占资源优先（`NFR-06-2`） |
| 断点续传 | `.part` 文件 + `Range: bytes=<n>-`，校验 `Content-Range` 与 `ETag` 一致 | `[文档]` GitHub CDN 支持 Range |
| 重试 | 指数退避 `1s→2s→4s` + ±20% 抖动，最多 3 次；仅 5xx/超时/连接重置重试 | 避免惊群 |
| 限速 / 并发 | `x/time/rate`，默认不限；下载并发 1（可配 1–3），安装并发恒为 1 | `NFR-06-1` |
| 超时 | 连接 10 s、首字节 30 s、空闲读 60 s（**非总时长**） | 大文件不能设总超时 |
| 代理 | 显式配置 > `HTTPS_PROXY/HTTP_PROXY` > 注册表 `Internet Settings`（`ProxyEnable/ProxyServer/AutoConfigURL`）> PAC（`WinHttpGetProxyForUrl`）`[文档]` | Go 的 `ProxyFromEnvironment` **不读 PAC**，必须自补 |
| 磁盘预检 | `GetDiskFreeSpaceExW`：需 `size × 2.5`（下载 + 解压峰值）+ 200 MiB 余量 | 提前失败好过装到一半 |
| 落盘 | 64 KiB 缓冲流式写，全程不整文件入内存 | `NFR-06-2` |

**结论**：默认路径必须是「单连接 + 流式 + 恒定内存」；分段下载是可选优化而非默认，否则低带宽用户与 SSD 寿命都要付出代价。

**为什么 v1 不做多分段（明确记录，避免日后被当成「偷懒」）**：GitHub Release 资产由 CDN 提供、`Range` 支持可靠，但分段下载的收益只在「**单连接被限速**」时才显著；本产品下载并发上限 3、且用户常在后台下载，分段带来的复杂度（分片校验、失败重试边界、临时文件管理、`ETag` 变更时的分片失效）与 `NFR-06-1` 的资源约束不匹配。故 v1 只保留「>32 MiB 可选 4 段」这一受限能力，其余情况单连接，性能问题留 `TBD-06-12` 观察真实用户数据后再定。`[待验证]`：GitHub CDN 是否对**同一客户端并发连接**限速——若限速则分段收益成立，若不限速则分段纯属浪费。

| 校验项 | 来源 | 失败策略 |
|---|---|---|
| `sha256` 摘要文件 | Release 里的 `SHA256SUMS` / `*.sha256`，按文件名匹配 | **硬失败** |
| Release asset `digest` | API `assets[].digest` = `sha256:…`（较新字段）`[待验证]` | 存在即**硬失败** |
| cosign `.sig`/`.pem`/`.cert` | 同 Release | v1 只记录存在性不验证（Sigstore 栈过重）`[文档]` |
| Authenticode | `WinVerifyTrust` + `WINTRUST_ACTION_GENERIC_VERIFY_V2` | **有签名但验证失败/吊销 → 硬失败，且不提供任何「仍要安装」入口；无签名 → 警告 + 强制二次确认 + 标红** |
| 发布者一致性 | 对比 `PublisherHistory`（docs/01 §3.7）中的历史签名主体 | 见下方「换签三层策略」，结果落 `VerifyResult` / `VerifyPolicy` |

**校验优先级（硬性规则，不得调换）**：

1. **哈希优先于签名**：只要上游提供了 SHA256（Release asset digest 或 checksums 文件），哈希校验就是**强制**的；只有在**上游确实未提供任何哈希**时才降级为「仅签名校验」。**不能因为包没签名就跳过哈希**——签名回答「谁发布的」，哈希回答「内容是否完整且未变」，两者不可互相替代。
2. **签名主体一致性**：若同一仓库的历史版本曾以某发布者签名、而新版本签名主体变了，默认**硬失败**。这是供应链投毒最典型的信号——开源包**不签名**可容忍（生态现实），但「**换了签名人**」默认不可容忍。合法换签（公司改名、证书轮换、仓库转组织）走下述三层策略，**逃生门在目录运营侧，不在用户侧**。

**换签三层策略（把逃生门从「用户」移到「目录运营」）**

**第 1 层 · 默认硬失败**：检测到主体变更即 `VerifyPolicy.HardFail`，UI **不渲染任何继续按钮**，只显示「该软件的签名发布者已变更」+ 旧主体 / 新主体（可复制）+「这可能是正常的证书轮换，也可能是软件被替换。请谨慎。」

**第 2 层 · 运营白名单（唯一合法通道）**：引入**发布者轮换白名单**，条目 `{appId, fromThumbprint, toThumbprint, reason, reviewedAt}`。
- 数据形态：随**内置种子数据 / 签名后的目录更新**下发；**由商店维护者审核后签发，不来自用户输入、不来自网络即时响应、不在本地可编辑**。
- 命中 → 策略降为 `VerifyPolicy.WarnConfirm`（提示「发布者已变更（已审核：<reason>）」，用户确认后继续）。
- **这不是「忽略校验」，而是「换签这件事已被人工确认」**：哈希校验仍强制、签名有效性仍强制，仅「主体一致性」这一项被白名单豁免。
- **存储与校验要求**：必须随签名产物下发（本地文件伪造无效）；加载时校验来源签名；白名单缺失或签名不可信 → **回退到硬失败（fail-closed）**。

**第 3 层 · 用户侧反馈（非绕过）**：硬失败页提供「报告此问题」，生成含 `appId / 旧主体 / 新主体 / 两个指纹` 的报告并引导到 issue 模板。**用户拿不到任何「继续安装」的路径。**

**为什么不用用户级「忽略校验」开关**：安全红线不可由用户解除——用户没有能力判断「换签」是证书轮换还是投毒，把判断权下放等于把 `RISK-06-9` 的防线交给最没有信息的一方；而运营侧有发布者沟通渠道与复核记录，能给出可审计的 `reason`。

| 情形 | `VerifyPolicy` | 用户可见 |
|---|---|---|
| 首次见到的发布者（`PublisherHistory` 无历史） | `VerifyPolicy.Proceed` | 正常 |
| 与历史一致 | `VerifyPolicy.Proceed` | 正常 |
| 变更且**未**在白名单 | **`VerifyPolicy.HardFail`** | 阻断 + 报告入口，无继续按钮 |
| 变更且**在**白名单 | **`VerifyPolicy.WarnConfirm`** | 提示已审核 + 确认继续 |

> 枚举拼写以 `docs/01 §3.7` 为准：`VerifyPolicy` 的三个值分别是 **`Proceed` / `WarnConfirm` / `HardFail`**（**没有** `Allow`——docs/08 §9 R2 门禁会断言这一点）。

**结论**：**「签名缺失」与「签名错误」必须区别对待**——开源项目大量不签名，硬失败会杀死产品；但「有签名却验不过」或「签名人换了」默认必须硬失败且**不给用户逃生门**；唯一的合法放行是运营侧审核过的白名单，且哈希与签名有效性**永不豁免**。

## 4. 安装策略（ADR-004）

### 4.1 三策略语义

| 策略 | 语义 | 前置条件 | 卸载方式 |
|---|---|---|---|
| `default` | 交给安装器/系统默认（`%LOCALAPPDATA%` 或 `C:\Program Files`） | 无 | 安装器自带卸载 |
| `custom` | 用户指定目录，仍走安装器（写注册表） | 包类型支持自定义路径（§4.2） | 安装器自带卸载 |
| `green` | 解压到目标目录，**不写注册表**，写 `.githubstore.json` + 快捷方式 | 资产为 `archive`/`portable-exe` | 删目录 + 快捷方式 + 清单 |

**结论**：三策略不是「三种偏好」而是「三种技术契约」——`custom` 是安装器的能力，`green` 是资产形态的属性，只有 `default` 永远可用。

### 4.2 包类型 × 策略可行性矩阵

| 包类型 | `default` | `custom` | `green` |
|---|---|---|---|
| `msi` | ✅ | ⚠️ 仅当包有 `INSTALLDIR/TARGETDIR` 且尊重 | ❌ |
| `msix` | ✅（固定 WindowsApps） | ❌ | ❌ |
| `exe-nsis` | ✅ | ✅ `/D=` | ⚠️ 需 7-Zip 解包，不可靠 `[待验证]` |
| `exe-inno` | ✅ | ✅ `/DIR=` | ⚠️ 同上 |
| `exe-squirrel` | ✅（固定 `%LOCALAPPDATA%`） | ❌ | ❌ |
| `exe-installshield` / `exe-wixburn` | ✅ | ⚠️ 仅 MSI 包装 / bundle 声明变量 | ❌ |
| `archive` | ✅（解压到默认目录） | ✅ | ✅ **首选** |
| `portable-exe` | ✅（复制） | ✅ | ✅ |
| `script` | ⚠️ 需确认 | ⚠️ | ❌ |
| `unknown` | ✅（交互） | ❌ | ❌ |

**不可行时的产品文案**（可直接使用）：`custom` 不可行 →「**该安装包不支持自定义安装位置**。它由 MSIX 打包，Windows 规定只能装在系统应用目录。你可以改为「绿色安装」（如果作者提供压缩包），或使用默认位置。」；`green` 不可行 →「**此应用没有可直接解压的版本**（只提供 `.exe` 安装程序）。绿色安装需要作者提供 `.zip`/`.7z` 包。你可以用默认安装，或**去官网**查看是否有免安装版。」；整体不可行 →「当前安装包类型无法识别，我们无法保证静默安装可靠，将以交互方式运行安装程序。」

**结论**：不可行时必须「**先解释再给替代路径**」，只置灰不给替代，用户会认为功能坏了。

### 4.3 路径校验规则（`custom` / `green` 共用，按序执行）

| # | 规则 | 失败处置 |
|---|---|---|
| 1 | 必须是绝对路径且含盘符；字符合法（无 `<>:"\|?*`、无结尾空格/点、非 `CON/PRN/AUX/NUL/COM1-9/LPT1-9`） | 拒绝，提示重选 |
| 2 | 禁止 UNC / 网络盘（`\\`、`\\?\UNC\`、`GetDriveType==DRIVE_REMOTE`） | 拒绝：「不支持安装到网络位置」 |
| 3 | 禁止受保护目录：`%SystemRoot%`、`System32`、`WinSxS`、`Program Files*`（未提权时）、盘符根、用户目录根 | 拒绝或强制提权 |
| 4 | 禁止 `%TEMP%`、Desktop、Documents、Downloads 作安装根（会被清理/同步） | 拒绝 |
| 5 | 长度：全路径 ≤ 240 字符；读 `HKLM\SYSTEM\...\FileSystem\LongPathsEnabled` | >240 警告；>260 且长路径未启用则拒绝 |
| 6 | 可写性探针：建 `.gs-write-probe` 再删；失败判定需提权 | 转提权或拒绝 |
| 7 | 已存在非空目录：含 `.githubstore.json` 且 `packageId` 相同 → 允许（升级/重装）；含他包清单 → 拒绝；无清单 → **二次确认**「该目录已有文件，继续可能与现有文件混合」 | 拒绝或确认后继续 |
| 8 | OneDrive 同步目录（`%OneDrive%` 前缀或 `HKCU\Software\Microsoft\OneDrive`） | 警告「同步可能导致安装失败或文件被按需占位」，默认不阻止 |
| 9 | 磁盘空间：`free >= estimated × 2.5 + 200 MiB` | 拒绝并给出可回收空间 |
| 10 | 归一化：`filepath.Clean` + 去尾分隔符 + 保留原始大小写 | — |

**结论**：路径校验必须**UI 侧实时校验 + 安装前再校验一次**（TOCTOU 兜底），且结果要能解释「为什么不行」，否则用户只会认为是 bug。

### 4.4 各安装器静默参数

| 类型 | 静默安装 | 自定义路径 | 静默卸载 | 注意 |
|---|---|---|---|---|
| MSI | `msiexec /i "x.msi" /qn /norestart INSTALLDIR="<dir>" ALLUSERS=1` | 属性名须从 MSI Property 表读（`INSTALLDIR/TARGETDIR/APPDIR/INSTALLLOCATION`）`[文档]` | `msiexec /x "{GUID}" /qn /norestart` | `/l*v` 日志体积大 |
| NSIS | `setup.exe /S /D=<dir>` | `/D=` **必须最后、不带引号、无尾反斜杠** | `uninstall.exe /S` | 顺序错会被当成路径 |
| Inno Setup | `setup.exe /VERYSILENT /SUPPRESSMSGBOXES /NORESTART /DIR="<dir>"` | `/DIR=` 引号可选 | `unins000.exe /VERYSILENT /SUPPRESSMSGBOXES` | `/LOG="f"` 可排障 |
| Squirrel | `Setup.exe --silent` | **不支持** | `Update.exe --uninstall` 或删 `%LOCALAPPDATA%\<App>` | 固定 `%LOCALAPPDATA%` |
| WiX Burn | `bundle.exe /quiet /norestart InstallFolder="<dir>"` | 仅当 bundle 声明该变量 | `/quiet /uninstall` | 变量名随包而变 `[待验证]` |
| InstallShield | `/s /v"/qn INSTALLDIR=\"<dir>\""`（Basic MSI）；InstallScript 用 `/s /f1"<iss>"` | 部分支持 | `/s /x` | 响应文件需预生成 |
| MSIX | `Add-AppxPackage -Path "x.msix"`（或 WinRT `PackageManager`） | **不可选**，固定 `WindowsApps` | `Remove-AppxPackage` | 未签名报 `0x800B0109` |
| ZIP/7z | 解压到 `<dir>` + 写 `.githubstore.json` + 建快捷方式 | 即目标目录 | 删目录 + 快捷方式 + 清单 | 见 §4.5 |

**结论**：参数表是「契约」，必须集中为一张 `installerSpec` 表（类型 → 模板 + 校验器），**禁止在调用点手拼命令行**，否则 NSIS 的 `/D=` 位置错误会反复出现。

### 4.5 绿色安装完整定义

目录布局：`<InstallDir>\` 下为解压出的应用文件 + `.githubstore.json`（引擎清单，唯一真相）。清单字段：`schemaVersion`、`sourceInstanceId`、`sourceEntryUrl`、`sourceRevision`、`packageId`、`displayName`、`version`、`channel`、`installerId`、`origin:"store"`、`strategy:"green"`、`installedAt`、`assetUrl`、`assetName`、`installerSha256`、`exePath`（主程序相对路径）、`shortcuts[]`、`elevated:bool`。

**提权**：仅当目标目录不可写（如 `C:\Program Files`）时需要；默认推荐 `%LOCALAPPDATA%\Programs\<App>`，全程免提权。**卸载** = 删 `<InstallDir>` + 删 `%APPDATA%\Microsoft\Windows\Start Menu\Programs\GitHubStore\*.lnk` + 从 `installed.json` 移除。**「用户手动删了目录」检测**：扫描时若 `installed.json` 有记录但 `InstallDir` 不存在 → 标 `state=broken`，UI 显示「记录残留」并给「清理记录」按钮（**不自动删**，避免把临时离线盘误判为删除）。

**结论**：绿色安装的价值在于「**卸载无残留、可回滚**」，因此清单必须落在安装目录内（随目录一起消失），而不是只存在于中心数据库。

## 5. 安装事务

### 5.1 状态机与 journal

状态：`Queued → Resolving → Downloading → Verifying → AwaitingElevation → Installing → Registering → Done`；任意阶段 → `Failed | Cancelled | RolledBack`；`Installing` 后异常 → `Partial`（docs/01 §7）。

```csharp
/// <summary>只追加的安装日志，表结构见 docs/01 §5.2 journal。</summary>
public sealed record JournalRecord
{
    public long Seq { get; init; }              // 单调递增，重放取最大
    /// <summary>幂等键 = sha256(appId|version|strategy|targetDir)</summary>
    public required string TaskId { get; init; }
    public required InstallState State { get; init; }
    /// <summary>如 "download:resume@1048576"</summary>
    public string? Step { get; init; }
    /// <summary>仅首条有值，保证崩溃后能自恢复出完整计划</summary>
    public InstallPlan? Plan { get; init; }
    public required DateTimeOffset At { get; init; }
}
```

**写入方式（v0.3 改动）**：v0.2 用 `journal.jsonl`（`O_APPEND` + `fsync` 每行）。v0.3 **改为写入 SQLite `journal` 表**（docs/01 §5.2），理由：
1. 单进程下已有 SQLite，再维护一个 append-only 文件等于两套持久化。
2. 事务性更好：`INSERT` + 提交是原子的；JSONL 的「半行写入」需要额外处理。
3. 便于查询（「找所有非终态记录」是一条 SQL，而不是全文件扫描）。

**语义不变**：**先写「意图」再执行**（`Installing:begin` → 执行 → `Installing:ok`），保证崩溃时能判断「是否已开始」。

**恢复流程（启动时 `RecoverJournalAsync`）**：查询所有非终态记录 → 若 `Installing` 已 begin 未 ok → 进入「疑似部分安装」，扫注册表/目录确认 → 成功则补 `Done`，否则标 `Partial` → 保留最近 200 条或 30 天，其余归档删除。

**提权事务的 journal（v0.3 删除了双写）**：v0.2 因提权进程是独立进程、无法写主进程的库，所以要另写 `%ProgramData%` 下的 JSONL。v0.3 直启安装器，**所有 journal 写入回到主进程**，只有一份，无跨权限写问题。

### 5.2 幂等 / 并发 / 取消 / 回滚

| 主题 | 设计 |
|---|---|
| 幂等 | `TaskId` 已在 `Done` → 直接返回缓存结果，不重复安装 |
| 并发锁 | 进程内 `SemaphoreSlim(1,1)` 串行化所有安装（**安装并发恒为 1**，见 §9） |
| 取消（`Queued`..`Verifying`） | `ct.Cancel()` + 删 `.part` → `Cancelled`，无残留 |
| 取消（`Installing`） | **不能安全中止**：只置 `CancelRequested` 等安装器返回；`0` → 按已装处理并提示；非 `0` → 回滚或标部分安装。**禁止 `Kill` msiexec**（会留下损坏的 MSI 状态）。例外：若安装器挂起超时且用户明确选择「强制结束」，才 `Kill(entireProcessTree: true)` 并标 `Partial` |
| 回滚 | `Green`/`Archive`：删目录 + 快捷方式（完全可回滚）；`Msi`：MSI 自身回滚；`Msix`：`Remove-AppxPackage` 补偿；`Nsis/Inno/Squirrel/InstallShield`：**无内置回滚** → 标 `Partial` + 提示「建议从控制面板卸载后重试」 |
| 部分安装 | `InstallRecord.State = Partial`，UI 显示黄色「安装可能不完整」+「重新安装」 |

**结论**：事务的价值不在于「永不失败」，而在于**失败后用户和引擎都确切知道机器处于什么状态**——所以 journal 必须先写意图再执行。

## 6. 提权与子进程执行（ADR-006，**v0.3 重写**）

> **决策：主程序永不整体提权；需要时用 `Verb="runas"` 直接启动安装器本体；只有通过完整校验链的文件才允许 `runas`。**

### 6.1 为什么放弃「独立提权 helper 进程」

v0.2 的方案是：低权限主进程生成 `InstallPlan` → 写文件 + HMAC → `ShellExecuteW` 启动 `gs-elevate.exe`（提权）→ helper 校验 HMAC 与白名单动作后执行 → 命名管道回传进度。

**v0.3 移除它的理由**：
1. **架构前提消失**：helper 是 Go 二进制，单进程 C# 后维护一个额外的跨语言产物不再划算。
2. **它保护不了真正的风险点**。白名单限制的是「helper 能执行哪些动作」，但一旦 helper 调用 `msiexec /i`，**真正做事的仍是第三方安装器**，helper 对它的行为毫无约束。白名单给出的是「受控」的错觉。
3. **拿到的进度信息有限**：多数安装器不输出可解析的进度，helper 转发的 stdout 往往是空或乱码。

**诚实记录代价（相对 v0.2 的安全退步）**：v0.2 至少能保证「提权进程不会联网、只执行枚举动作、plan 一次性」；v0.3 直启安装器后，**提权后的行为完全由第三方安装器决定**。这是所有商店类软件（含 winget、Store）的共性，不是本项目缺陷，但必须写明。

### 6.2 唯一有意义的防线：提权与校验强绑定

```csharp
// 硬规则：runas 的唯一前置条件
if (verifyResult.Policy != VerifyPolicy.Proceed &&
    verifyResult.Policy != VerifyPolicy.WarnConfirm /* 已二次确认 */)
    throw new AppException("verify.hard_fail");   // 不可能走到 runas

if (!FileIntegrity.HashOk || verifyResult.SignatureState is SignatureState.None
                                              or SignatureState.Invalid
                                              or SignatureState.Revoked)
    throw new AppException("elevate.requires_verified_binary");
```

**规则**：`Policy == HardFail` 的文件**永不进入 `runas` 分支**（docs/07 红线）。无签名文件也不提权——即使哈希匹配，因为提权执行无签名文件的收益远小于风险。

### 6.3 两种执行模式

| 模式 | 配置 | 能否拿 stdout | 能否拿进度 | 适用 |
|---|---|---|---|---|
| **A 非提权（推荐）** | `UseShellExecute=false`<br>`RedirectStandardOutput=true`<br>`ArgumentList`（**不用 `Arguments` 字符串**） | ✅ | ✅ 可解析的安装器 | 用户级安装（`%LOCALAPPDATA%`）、绿色安装、winget |
| **B 提权** | `UseShellExecute=true`<br>`Verb="runas"`<br>**无法重定向** | ❌ | ❌ 只能靠检测目标目录/注册表变化推断 | 机器级安装（`Program Files`、`HKLM`） |

**模式 B 的代码与限制**：

```csharp
var psi = new ProcessStartInfo
{
    FileName        = installerPath,
    UseShellExecute = true,      // runas 必须为 true
    Verb            = "runas",
};
foreach (var a in safeArgs) psi.ArgumentList.Add(a);   // UseShellExecute=true 时 ArgumentList 仍可用

try
{
    using var p = Process.Start(psi);
    if (p is null) throw new AppException("install.spawn_failed");
    await p.WaitForExitAsync(ct);       // 提权进程无法读 stdout
    return p.ExitCode;                  // [待验证] runas 启动的进程能否可靠拿到 ExitCode
}
catch (Win32Exception ex) when (ex.NativeErrorCode == 1223)  // ERROR_CANCELLED
{
    throw new AppException("elevate.user_cancelled");  // → Cancelled，不是 Failed
}
```

**矩阵：包类型 × 是否需提权 → 用哪个模式**

| 包类型 / 场景 | 需提权 | 模式 | 能拿到 | 进度回报方式 |
|---|---|---|---|---|
| MSI（per-user） | 否 | A | stdout + 退出码 | msiexec `/L*v` 日志解析 |
| MSI（per-machine，`ALLUSERS=1`） | **是** | B | 仅退出码 | 轮询注册表 `InstallLocation` / 目录大小变化 |
| NSIS / Inno（用户目录） | 否 | A | stdout + 退出码 | 安装器自身输出（多数有） |
| NSIS / Inno（`Program Files`） | **是** | B | 仅退出码 | 目录变化轮询 |
| Squirrel | 否 | A | stdout | 目录变化 |
| MSIX（`Add-AppxPackage`） | 视 `-Scope` | A（`-Scope CurrentUser`） | PS 输出 | 无进度，只有阶段 |
| ZIP / 7z（`Green`） | 否 | **A（不启子进程，直接解压）** | 完全可控 | 逐文件进度 |
| winget | 视包 | A | ✅ 有结构化输出 | 解析 winget 输出 |
| 任意（挂起超时后） | — | — | — | 提示用户可「放弃等待」 |

> **结论**：模式 B（提权）是**信息最少**的路径，但它覆盖的是「必须装到系统目录」的场景，无法回避。产品上必须接受「提权安装时进度条是估算的」这一事实，并在 UI 上明确标注（docs/04 §5）。

### 6.4 子进程防御（**v0.3 新增，本章最重要的工程内容**）

安装器是第三方代码，行为不可控。`IProcessRunner` 必须处理：

| 风险 | 表现 | 对策 | 实现要点 |
|---|---|---|---|
| **stdout 管道死锁** | 子进程写满 4KB 缓冲区后阻塞，我们等它退出 → 互等 | 先起异步读取，再 `WaitForExitAsync` | `BeginOutputReadLine()` + `OutputDataReceived` 事件，或 `Task.Run(() => ReadLineAsync 循环)` |
| **安装器挂起** | 卡在对话框 / 网络等待 / 死锁 | 心跳超时：同阶段 10 分钟无输出 → 提示「安装器可能卡住」，给「继续等待 / 放弃」 | `CancellationTokenSource.CancelAfter` + 最后输出时间戳 |
| **宿主崩溃/被强杀** | 第三方安装器可能仍在运行 | 不给真实安装器设置 `KILL_ON_JOB_CLOSE`；journal 先落盘，重启后标记 `Unknown/Partial` 并对账 | Job Object 仅用于商店自有且可安全终止的辅助进程/测试进程 |
| **句柄泄漏** | 反复安装后句柄数增长 | `using var p = Process.Start(...)`；显式 `Dispose` 事件订阅 | 单元测试断言句柄数稳定 |
| **UAC 被拒** | 抛 `Win32Exception(1223)` | 归类为「用户取消」而非「失败」 | 不标 `Failed`，允许重试 |
| **退出码无意义** | 安装器返回 0 但实际失败 | **必须事后校验**：注册表项 / `InstallLocation` / 目录存在 → 才算成功 | 见 §5 状态机 `Registering` 阶段 |

**Job Object 边界**：可以限制商店自有下载辅助进程或测试替身的资源并在宿主退出时回收；不得把 MSI、MSIX、winget 或任意第三方安装器加入 kill-on-close job。`WaitForExitAsync(ct)` 的取消仅取消等待，不代表安装器已停止。

### 6.5 拒绝提权的降级路径

`ERROR_CANCELLED (1223)` → 提示「该应用需要管理员权限；你可以改为**绿色安装**（若提供压缩包）或安装到用户目录」，事务置 `Cancelled`（可重试），**不标 `Failed`**。

> **结论**：v0.3 的提权边界从「白名单动作 + HMAC plan + 独立进程」退化为「**校验通过才能 runas**」这一条。它更简单，但也更弱——**这是单进程架构的直接代价**，必须让评审知道。真正的兜底不在提权层，而在**校验层**：确保以管理员身份运行的那个文件确实是我们校验过的那个文件。

## 7. 已安装检测与更新

### 7.1 扫描源

| 源 | 读取方式 | 关键字段 | 成本 |
|---|---|---|---|
| 注册表 Uninstall | `Registry.LocalMachine/CurrentUser.OpenSubKey(@"SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall")` + `WOW6432Node` + `RegistryView.Registry32/64` | `DisplayName/DisplayVersion/InstallLocation/Publisher/UninstallString/QuietUninstallString/DisplayIcon/EstimatedSize` | 低（<50 ms） |
| MSIX 清单 | `PackageManager.FindPackagesForUser`（WinRT）或 `AppModel\Repository\Packages` | `PackageFullName/Version/InstallLocation` | 中 |
| winget 对账 | `winget list --id <Id> -e`（按需） | 版本、可用更新 | 高（起进程），**禁止全量轮询** |
| 商店自有清单 | SQLite `install_records` 表 | 完整 `InstallRecord` | 极低 |

> **注册表注意**：.NET 中读 32/64 位视图必须显式用 `RegistryKey.OpenBaseKey(RegistryHive.LocalMachine, RegistryView.Registry64)`，否则在 x64 进程下默认只看到 64 位视图（`[文档]`）。SOFTWARE 键会被 WOW64 重定向，**必须三种视图都扫**（原生 64、WOW6432Node、HKCU）。

**结论**：扫描要「**按需 + 分级**」——打开已安装页只跑注册表与自有清单（60 s 缓存），MSIX 与 winget 对账惰性触发；扫描在线程池以 `ThreadPriority.BelowNormal` 或分批 `await Task.Yield()` 执行，避免与 UI 抢 CPU。

### 7.2 版本比较

去 `v` 前缀 → 匹配 SemVer 2.0 则按 SemVer（`1.0.0-beta < 1.0.0`）→ 否则四段数字补齐（`1.2` = `1.2.0.0`）→ 否则按日期（`2024.10.18`）→ 全不匹配则**不可比较**。

> **v0.3**：正式实现见 docs/01 §3.4 的 `Version` record 与 `VersionComparer.Compare`；本节只描述降级链语义，不重复定义类型。

**不可比较时**：仍展示「有新版本」，但注明「版本号格式无法比较，按发布时间判断」，`UpdateInfo.Comparable = false`。

### 7.3 更新检查

更新首先查询安装记录绑定的软件源活动快照；源条目声明的 GitHub Release、winget 或固定 HTTPS 资产只是其上游/下载通道。官方源生成器可用 `/repos/{o}/{r}/releases/latest`（自动排除 draft/prerelease）刷新目录；客户端不得绕过原源直接把 GitHub API 结果变成可执行更新。频率：启动后延迟 30 s 检查一次（仅 `Origin.Store` 且有记录者），同包 24 h 内不重复，手动检查不受限。源刷新遇到 `403/429` 按 docs/10 退避并继续使用缓存；`UpdateInfo` 落 SQLite（`checkedAt` + 来源 revision），离线时展示缓存并标「上次检查：x 小时前」。

### 7.4 软件源绑定与切源

创建计划时必须从当前活动快照复制并冻结以下字段：`SourceInstanceId`、源入口 URL、`PackageId`、`SourceRevision`、`releaseKey`、通道、版本、`installerId`、安装策略和目标路径；HTTP 通道冻结资产 URL/SHA-256，winget 通道冻结 package ID/version。执行时按 `planId` 读取这份冻结记录并复校，不能重新按显示名或仓库地址解析到“当前看起来最新”的其他条目。

安装完成后同样把这些字段写入 `install_records` 和绿色安装的 `.githubstore.json`。更新检查默认只查询原 `SourceInstanceId + PackageId + channel`：

- 源被禁用、移除或暂时失败：返回 `UpdateState.Unavailable`/`Unknown`，保留现有安装和卸载能力。
- 原源已移除该条目：显示“原软件源不再提供此软件”，不自动找同名来源。
- 其他源提供更高版本：只显示“其他来源有版本”，用户进入对比页显式确认后才迁移绑定。
- 切源确认必须重新展示新源信任等级、发布者、权限、通道、哈希和安装策略；它是新的安装决策，不是普通刷新。

源签名只验证目录发布者，不能替代资产的 SHA-256 与 Authenticode 校验。来源规则以 docs/10 为准。

### 7.5 origin 判定（关键产品规则）

> **只有 `Origin.Store` 的记录才渲染「更新 / 卸载」；其余只读展示「已安装」+「去官网」。**

按序判定，命中即停：① SQLite `install_records` 有该 `AppId` 记录，且 `installerSha256` 与当前安装器 hash 一致，且 `installPath` 与注册表 `InstallLocation` 一致 → **`Origin.Store`**；② 记录在但 `installPath` 不同 → `Origin.Store` 且 `drifted=true`（用户改过位置）→ 仍给更新/卸载，但按记录路径卸载并提示；③ 记录在但注册表项消失、目录仍在 → `state=broken`，给「清理记录」；④ 注册表有同名项但无商店记录（或 `UninstallString` 指向别处）→ **`Origin.External`**：显示「已安装（非商店管理）」，**不给**更新/卸载，只给「去官网」；⑤ 用户手动装了同一软件（版本更高）→ 仍 `external`，但商店页提示「检测到你已手动安装 vX，是否接管？」——**接管需显式确认**，确认后写记录。

**结论**：origin 是**证据链**（清单 + hash + 路径），不是「名字匹配」。宁可把商店装的误判为 external（少给按钮），也不能把用户自装的误判为 store（误删用户软件，是不可接受的事故）。

**为什么是单向保守（产品红线，措辞固定）**：两类误判的**后果严重性不对称**——误判为 `external` 的代价是「用户少看到两个按钮，可手动重新关联」；误判为 `store` 的代价是「卸载了用户自己装的软件」。前者是可恢复的体验降级，后者是不可逆的数据事故，因此判定逻辑**只允许向 external 一侧倾斜**。

**卸载前指纹兜底（即使 Origin.Store 也要拦一道）**：执行卸载前，重新核对 `InstallRecord.Fingerprint`（`AppId + installerSha256 + installPath + 卸载注册表项签名`）与当前磁盘/注册表事实；其中 `AppId` 包含 `SourceInstanceId + PackageId`。**若不一致，即使 `Origin.Store` 也必须二次确认**，并显示「该软件可能已被外部修改（版本/路径/安装来源与记录不符），继续卸载可能影响你自己安装的版本」。

## 8. 卸载

| 场景 | 命令 | 备注 |
|---|---|---|
| 有 `QuietUninstallString` | 直接执行 | 优先，最省事 |
| MSI | 从 `UninstallString` 提取 `{GUID}` → `msiexec /x "{GUID}" /qn /norestart` | `/I` 型必须改写为 `/X` |
| 其他 exe | 追加 `installerSpec` 静默参数 | 交互式卸载器则提示「将打开卸载程序」 |
| winget 装的 | `winget uninstall --id <Id> -e --silent --disable-interactivity` | 与 §2.5 共用退出码表 |
| 绿色安装 | 删目录 + 删快捷方式 + 删清单 | 纯文件操作，除 Program Files 外免提权 |

**残留清理**：安装目录卸载后仍在 → 提示「是否删除残留目录」；`%APPDATA%`/`%LOCALAPPDATA%` 用户数据**默认保留**（卸载对话框给「同时删除应用数据」复选框，默认不勾）。卸载后注册表项消失但 SQLite `install_records` 仍有记录 → 自动移除记录并提示「已卸载」。**失败处理**：返回非 0 → **不删记录**，标 `InstallState.Failed`（含 `uninstall_failed` 明细） + 原始退出码，并提供「强制移除记录（保留文件）」出口，避免用户被卡死。

**结论**：卸载的默认姿态是「保守」——先不删用户数据、先不删记录，把不可逆动作全部交给用户显式确认。

## 9. 错误分类与用户文案

| 类别 | 码前缀 | 一句话原因 | 可执行动作 | 可重试 |
|---|---|---|---|---|
| 网络 | `NET-` | 下载失败（超时/断流/代理不可用） | 检查网络/代理后重试，支持续传 | ✅ |
| 校验 | `VER-` | 安装包校验失败，可能被篡改或下载不完整 | 重新下载；连续失败 2 次则拒绝 | ✅ 限 2 次 |
| 签名 | `SIG-` | 安装包签名无效或发布者变更 | 阻止安装，提示来源风险 | ❌ |
| 权限 | `PERM-` | 需要管理员权限 / UAC 被取消 | 提权重试，或改绿色/用户级安装 | ✅ |
| 安装器 | `INST-` | 安装程序返回错误（见 §2.5） | 展示原始码 + 打开日志目录 | 视码 |
| 磁盘 | `DISK-` | 空间不足 / 路径不可写 | 换目录或清理空间 | ✅ |
| 未知 | `UNK-` | 未预期错误 | 附诊断包（journal + 日志）反馈 | ✅ |

**文案原则**：**一句话说人话 + 一个可点的动作 + 原始错误码折叠进「详情」**；禁止把 `0x8A1500xx` 直接当主文案甩给用户。

## 12. 与其他章节的接口

**对 docs/02（架构）的假设**：引擎为 `GitHubStore.Core/Install` 类库，与 UI **同进程**；UI 只通过 DI 注入的 `IInstallService`（docs/01 §4）依赖 §0 的 `API-06-x`，**UI 不直接启动任何安装器**；架构需提供单实例守护、安装任务串行化（`SemaphoreSlim`，同时仅 1 个安装）、`CancellationToken` 取消传播、结构化日志、`IProgress` 进度节流（≤20 次/秒），以及 `IProcessRunner`（超时/心跳/Job Object）。**v0.3 已无 `gs-elevate.exe`**。

**对 docs/01、docs/05 与 docs/10 的假设**：docs/01 提供 `AppId`、`ReleaseKey`、`InstallerId`、`SourceBinding` 及持久化契约；docs/10 的活动完整快照提供版本和安装器候选，docs/05 只负责官方源的上游发现/生成与 GitHub 展示元数据。winget `Id` ↔ GitHub 仓库只是策展映射，不替代 `AppId`。网络层统一重试、限流和认证；GitHub Token 只发往 `api.github.com`。

**对 docs/07（安全）的假设**：本章签名策略（缺失警告 / 错误硬失败）需 docs/07 复核并最终裁决；**`runas` 直启安装器的威胁需要 docs/07 重新建模**（v0.2 的「提权 helper 白名单」已不存在）；假设 docs/07 提供 DPAPI 封装用于凭据与安装器 hash 指纹存储；假设 docs/07 明确「第三方安装器 = 任意代码执行」的免责声明与用户确认流程。
