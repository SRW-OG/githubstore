## 本章结论（TL;DR）

1. **技术栈已由用户指定**：WinUI 3（Windows App SDK）+ C#，XAML 做界面、C# 写业务逻辑，**单进程**。本章不再讨论「用哪个 UI 框架」——那是已决事项。
2. **推荐组合**：**.NET 8 LTS + Windows App SDK 1.6 + 非打包（unpackaged）+ framework-dependent + CommunityToolkit.Mvvm**。选 .NET 8 而非 .NET 9 是看重 LTS 支持周期；选 unpackaged 是为了传统分发、显式文件布局和独立更新器集成，不把它误认为第三方安装器支持自定义路径的前提。
3. **`[待验证]` WinUI 3 的资源成本必须实测**：单进程空窗口 WorkingSet 估算 **60–90 MB**，浏览态 120–180 MB。这是 .NET 运行时 + XAML 视觉树的固有成本，**不是实现问题，也无法通过优化消除**。任何「WinUI 3 更省资源」的说法都不成立。
4. **单进程相对 v0.2 双进程的净效果**：**省掉一整套 Go 运行时（约 30–50 MB）与 IPC 开销，但托盘态无法再靠「UI 进程退出」省内存**——托盘必须由本进程持有。裁决见 §3.5.2。
5. **安装包体积 `[待验证]` 目标 ≤40 MB**：framework-dependent 下 UI 侧约 15–30 MB。若被迫改 self-contained，体积会到 90–170 MB，与 NFR-1.4 严重冲突。**这是需要负责人拍板的 Q-6**。
6. **最大工程风险从「IPC」变成「UI 线程纪律」**：v0.2 怕管道断连，v0.3 怕某个 `async` 方法在 UI 线程同步等待导致界面卡死。规避手段是编译器分析器 + code review 检查表（§3.4.4）。
7. **失去的能力必须记录**：进程级崩溃隔离、跨平台可能性、Go 生态的部分库。这三条是本次选型的实际代价，不粉饰。

## 3.2 四条工程组合路线

所有路线都满足「WinUI 3 + C# 单进程」的前提，差异在**部署形态与运行时策略**：

| 维度 | **路线 A**（推荐）<br>.NET 8 LTS + WASDK 1.6<br>unpackaged + framework-dependent | 路线 B<br>.NET 8 + unpackaged<br>self-contained | 路线 C<br>.NET 8 + **MSIX 打包**<br>framework-dependent | 路线 D<br>.NET Framework 4.8 + WASDK<br>（已否决） |
|---|---|---|---|---|
| .NET 运行时来源 | 系统已装（安装器引导） | 随包分发 | 系统已装 | 系统内置 |
| UI 侧体积（估算） | **15–30 MB** | 90–170 MB | 15–30 MB | 10–25 MB |
| 首次启动 | 1.5–2.5 s | 1.2–2.0 s | 1.5–2.5 s | 1.0–2.0 s |
| 自定义安装路径 | ✅ 完全可控 | ✅ | ❌ **装到 `WindowsApps`** | ✅ |
| 自更新 | ✅ 自建独立签名 updater（下载→校验→版本目录原子切换→重启） | ✅ | ✅ 由 MSIX 平台托管 | ✅ |
| 干净卸载 | ⚠️ 需自己实现（写 Uninstall 注册表项） | ⚠️ 同左 | ✅ 平台托管 | ⚠️ 同左 |
| 包身份 / 通知 / 关联 | ❌ 无包身份，部分 WinRT API 受限 | ❌ 同左 | ✅ | ❌ |
| 运行时缺失风险 | **有**（需引导安装） | 无 | 有 | 无（系统自带） |
| 与 NFR-1.4（≤40MB） | ✅ 达标 | ❌ **严重超标** | ✅ 达标 | ✅ 但见否决理由 |
| 与 FR-4.2（自定义路径） | ✅ | ✅ | ❌ **直接冲突** | ✅ |

**路线 D 否决理由**：
1. .NET Framework 4.8 上的 WinUI 3 需要额外的 C#/WinRT 投影与自包含配置，**工具链脆弱、社区案例少**（`[待验证]`）。
2. .NET Framework 已停止功能演进（仅安全更新），长期维护风险高。
3. 单文件发布、源生成器、`System.Threading.RateLimiting` 等现代库支持缺失，等于放弃 .NET 8 的全部工程收益。

**路线 C 否决理由（最关键）**：MSIX 安装到 `%ProgramFiles%\WindowsApps\`，**路径由平台决定，不可自定义**。这直接违反 FR-4.2「必须支持用户自定义安装路径」。为一个商店应用砍掉自己最核心的差异化功能，不可接受。

> **结论 → 路线 A**。代价是「需要处理运行时不存在的机器」，但这是可以**在安装器里用引导页解决**的问题（检测 → 提示 → 打开下载页 / 用 `winget install Microsoft.DotNet.DesktopRuntime.8`），而不是必须架构妥协的问题。

## 3.3 ADR-001：UI 技术栈与部署形态

| 字段 | 内容 |
|---|---|
| 编号 / 状态 | ADR-001 ／ **已决策（Accepted）**——v0.1 的「Wails v2」与 v0.2 的「WinUI 3 + Go 双进程」均已作废，见附录 A |
| 决策 | **WinUI 3（Windows App SDK 1.6）+ C# + .NET 8 LTS + 单进程 + 非打包（unpackaged）+ framework-dependent**；MVVM 用 CommunityToolkit.Mvvm；数据层 `Microsoft.Data.Sqlite` + 手写 SQL |
| 影响范围 | docs/02 全部（分层、线程模型、部署）；docs/00 的 NFR-1.x 口径；docs/04 的 DI 契约；docs/06 的提权方式；docs/09 的 ADR 索引 |
| 关联 | ADR-009（部署形态，本章细化）；ADR-011（单进程分层，docs/02）；ADR-006（提权，docs/06） |

**为什么是这四项搭配**

| 选择 | 理由 | 代价 |
|---|---|---|
| **WinUI 3** | 用户指定；原生 Fluent 观感；无障碍与 DPI 支持优于自绘；无 WebView2 依赖 | 需 Windows App SDK Runtime；XAML 视觉树内存成本高 |
| **单进程** | 用户指定；单栈维护；无 IPC/序列化开销；调试直观 | 丧失进程级崩溃隔离；无跨平台 |
| **unpackaged** | 传统分发、显式文件布局，便于集成独立 updater | 无包身份；卸载/快捷方式/关联需自己实现；部分 WinRT API 不可用；第三方安装路径仍取决于其安装器 |
| **framework-dependent** | 体积 15–30MB，唯一能接近 NFR-1.4 的方案 | 依赖系统 .NET + WASDK Runtime；缺失时首启失败 |

**后果（正）**
1. **单栈**：一个语言、一套构建、一个调试器。相比 v0.2 省去 IPC 协议设计、跨语言类型映射、双产物签名与版本对齐。
2. **启动更快**（理论上）：无第二个进程的启动与握手，无管道建立。
3. **内存可能更低**：省掉 Go 运行时（约 30–50 MB）。
4. **生态成熟**：.NET 的 HTTP/SQLite/JSON/测试/分析器全都是一等公民。

**后果（负，必须正视）**
1. **丧失崩溃隔离**：v0.2 里安装器崩溃不影响 UI；v0.3 里安装器仍在子进程（这部分保住了），但**我们自己的任何未捕获异常都会终止整个应用**。
2. **托盘态内存无法压缩**：托盘必须由本进程持有，关窗驻留就要吃满 60–110MB（§3.5.2 有裁决）。
3. **无跨平台可能**：v0.2 的 Go 核心理论上可移植；v0.3 彻底绑定 Windows。
4. **运行时依赖**：用户机器缺 .NET 8 时首启失败，必须在安装器里处理。
5. **XAML 学习曲线**：数据绑定、`ItemsRepeater` 虚拟化、`x:Load` 都有坑，且调试体验不如 Web。

**回退触发条件与阈值（可测量）**

| 触发条件 | 阈值 | 回退目标 | 依据 |
|---|---|---|---|
| 单进程内存超预算 | 浏览态 5 min 稳态 > 220 MB WS（P95） | 先做 §3.6 优化；仍超标 → 降低图片/虚拟化规格；再超标 → 重议 NFR-1.2 | TBD-03-1 |
| 冷启动超上限 | 到可交互 > 3.0 s（P95） | ReadyToRun + 延迟加载 + 首屏骨架；仍超标 → 重议 NFR-1.6 | TBD-03-2 |
| 体积超上限 | framework-dependent 仍 > 60 MB | 裁剪 + R2R 折中；仍超标 → 重议 NFR-1.4（Q-6） | TBD-03-3 |
| WinUI 3 在某版本 Win10 上无法启动 | 兼容矩阵测试失败率 > 5% | **改 WPF**（同 C# 单栈，体积更小，但失去 Fluent 观感） | TBD-03-5 |
| 单进程崩溃率不可接受 | 会话崩溃率 > 0.5% 且归因于本进程 | 考虑拆进程（重新引入 IPC，代价高）；或先加异常边界 | RISK-03-4 |

> **读法**：ADR-001 的验收门槛不是「WinUI 3 更好」，而是 **TBD-03-1/2/3/5 实测未越线**。**最可能先撞线的是 NFR-1.4（体积）与 NFR-1.1（托盘态内存）**，建议在 M0 阶段就测，不要等 UI 做完。

## 3.4 进程与线程模型（单进程版）

### 3.4.1 执行位置

```
githubstore-ui.exe
├─ UI 线程（DispatcherQueue）
│    XAML 布局/绘制、输入、无障碍、ViewModel 属性变更
│    ★ 禁止：任何同步 IO、任何 .Result/.Wait()
│
├─ 线程池（Task / async）
│    SQLite 查询、HTTP、哈希/签名校验、JSON 解析、AI 流解析
│    ★ 全部 async，全部接受 CancellationToken
│
└─ 子进程（Process.Start）
     第三方安装器（msiexec / setup.exe / winget）
     ★ 必须：超时、心跳、Job Object 回收
```

### 3.4.2 关键技术决策

| 场景 | 选型 | 理由 | 陷阱 |
|---|---|---|---|
| 异步模型 | `async/await` + `CancellationToken` | 语言级一等公民 | `.Result` 在 UI 线程必死锁；`async void` 异常不可捕获 |
| 进度回报 | `IProgress<T>`（用 `Progress<T>` 实现） | 自动捕获并回到 `SynchronizationContext`（UI 线程） | 自己手工 marshal 容易漏 |
| 后台队列 | `System.Threading.Channels.Channel<T>` | 无锁、背压友好、`ReadAllAsync` 支持 `await foreach` | 无界 channel 会 OOM，必须 `BoundedChannel` |
| 子进程 | `System.Diagnostics.Process` + `WaitForExitAsync` | 标准方案 | stdout 管道死锁（必须先起读取） |
| 子进程生命周期 | journal + 重启对账；Job Object 只管自有辅助进程 | 不强杀真实安装器，父进程死后状态可恢复 | `WaitForExitAsync` 取消仅停止等待 |
| 网络 | 单例 `HttpClient` + `SocketsHttpHandler` | 连接池复用、`PooledConnectionLifetime` 防 DNS 陈旧 | 不要每请求 new；桌面场景用 `IHttpClientFactory` 反而绕开连接复用 |
| HTTP 超时 | `HttpClient.Timeout = InfiniteTimeSpan` + `CancellationToken` | 避免全局超时误杀流式响应（AI 摘要） | 忘了给 `CancellationToken` 就等于永不超时 |
| 数据库 | `Microsoft.Data.Sqlite` + 单写连接 + WAL | 官方驱动、轻量、无 EF 开销 | 每次 `Open` 有成本；SQLite 写入必须串行 |
| JSON | `System.Text.Json` + **源生成器** | 零反射、裁剪友好、启动快 | 忘了 `[JsonSerializable]` 会静默回退到反射 |
| 日志 | `Microsoft.Extensions.Logging` + 自写文件 Provider | 结构化日志、可替换 | 引 Serilog 的体积换不来收益 |
| MVVM | `CommunityToolkit.Mvvm`（源生成器） | `[ObservableProperty]`/`[RelayCommand]` 零样板 | 源生成器要求类为 `partial` |

### 3.4.3 线程池配置

```csharp
// Program.Main 最先执行
ThreadPool.SetMinThreads(workerThreads: 16, completionPortThreads: 16);
```

**理由**：默认最小线程数等于 CPU 核心数，在「同时下载 2 个 + 查询 3 个 + 校验 1 个」的场景下会短时饥饿，导致进度更新卡顿（`[待验证]`）。设 16 是经验值，需基准测试确认（TBD-03-8）。

### 3.4.4 UI 线程纪律（五条硬规则，与 docs/02 §4.2 一致）

1. 禁止 `.Result` / `.Wait()` / `.GetAwaiter().GetResult()`。
2. 服务层方法全部 `async` + `CancellationToken`。
3. 进度用 `IProgress<T>`。
4. 服务层内部 `ConfigureAwait(false)`；UI/ViewModel 层不写。
5. `async void` 只允许事件处理器，且必须 try/catch。

**落地手段**（不只是文档约定）：
- **分析器**：`Microsoft.VisualStudio.Threading.Analyzers`（VSTHRD002「避免同步等待」、VSTHRD100「避免 async void」、VSTHRD110「观察 await 结果」）。这些规则能在编译期把违反第 1/5 条的代码报出来。
- **code review 检查表**：docs/08 列出必查项。
- **CI 门禁**：把相关规则设为 `TreatWarningsAsErrors`。

> **结论**：v0.3 的线程纪律**必须靠工具强制**，不能靠自觉。VSTHRD 系列分析器是本章最有价值的工程建议——它把「UI 卡死」这类最难复现的 bug 挡在编译期。

## 3.5 内存与资源预算

### 3.5.1 三态预算（**估算，目标值，非实测**）

口径：**单个 `githubstore-ui.exe` 进程**；`WorkingSet64`（WS）与 `PrivateMemorySize64`（PM）分别报告。

| 指标 | 托盘空闲（窗口隐藏） | 浏览列表 | 边下边装 |
|---|---|---|---|
| WorkingSet | 110 / 150 MB | 170 / 220 MB | 200 / 260 MB |
| PrivateMemory | 160 / 210 MB | 230 / 300 MB | 270 / 340 MB |
| 句柄数 | 400 / 700 | 900 / 1500 | 1100 / 1900 |
| 线程数 | 20 / 35 | 40 / 80 | 50 / 100 |
| CPU（1 min 均值） | 0.05% / 0.5% | 0.3% / 1.5% | 3% 均值 / 25% 峰值 |
| 磁盘占用增量 | 20 MB | 200 MB（DB + 图标缓存） | +400 MB（临时下载区） |
| 启动到可交互 | 0.5 / 1.0 s（窗口重建） | 2.0 / 3.0 s（冷启动） | 不适用 |

**分解（浏览态 170 MB 的来历，`[待验证]`）**：

| 组成 | 估算 | 说明 |
|---|---|---|
| .NET 运行时基线 | 25–35 MB | 运行时 + GC 堆初始 |
| WinUI 3 框架 | 25–40 MB | `Microsoft.UI.Xaml.dll` + Windows App SDK |
| XAML 视觉树（1000 条虚拟化） | 20–35 MB | 只算可视区 + 缓冲 |
| 图标缓存（内存） | 10–20 MB | 按需解码、限制尺寸 |
| SQLite + 查询结果 | 10–25 MB | 分页加载 |
| 业务对象 | 10–20 MB | `App`/`Asset` 对象 |
| 余量 | 15–30 MB | — |

### 3.5.2 托盘态的矛盾与裁决（**本次架构变更的核心取舍**）

单进程下托盘只能由本进程创建，因此「关窗即退出」与「托盘常驻」不可兼得：

| 方案 | 关窗行为 | 空闲 WS | 后台检查更新 | 综合评价 |
|---|---|---|---|---|
| **A 关窗即完全退出** | 进程终止，**托盘消失** | 0 MB | ❌ 只能启动时检查 | 内存最优，但砍掉 FR-8 的后台价值 |
| **B 关窗隐藏到托盘**（**裁决采用**） | 窗口隐藏，进程驻留 | **60–110 MB** | ✅ | 符合商店类应用预期；秒开 |
| C 关窗退出 + 快速启动优化 | 进程终止 | 0 MB | ❌ | 需要预热优化，收益不确定 |

**裁决：默认 B（关窗隐藏到托盘），设置中提供「关闭窗口时退出应用」开关切到 A。**

理由：
1. **产品语义**：用户装的是「软件商店」，核心场景包括「后台检查更新并提醒」。方案 A 让更新提醒变成「打开应用才知道」，直接削弱 FR-8。
2. **内存代价已被接受**：Q-6 的取舍本身就包含「接受 WinUI 3 的资源成本」。
3. **低配用户有退路**：设置开关可切 A，且界面会说明「开启后无法后台检查更新」。

**方案 B 必须实现的三件事**（否则「隐藏」等于没省）：
1. **隐藏时卸载视觉树**：不能只 `Window.Hide()`。应导航到空白页并清空 `ItemsSource`，让列表项的视觉对象被回收。
2. **隐藏时停止所有定时器**（NFR-1.7 空闲 CPU ≈0%）。
3. **托盘「退出」必须真退出**：取消所有 `CancellationTokenSource` → 等待后台任务（≤3s）→ 若有安装进行中二次确认 → `Application.Exit()`。

> **诚实记录**：这是 v0.3 相对 v0.2 的**明确退步**。v0.2 靠「托盘归 Go、UI 关窗即退」能到 30–50 MB；v0.3 单进程必须驻留 60–110 MB。**这是「单进程 + C# 业务」决策的直接后果**，不是可以通过优化消除的。

### 3.5.3 与 NFR-1.4（体积）的关系

| 部署方式 | UI 侧体积（估算） | 与 NFR-1.4（≤40MB） |
|---|---|---|
| **framework-dependent**（推荐） | **15–30 MB** | ✅ 达标 |
| self-contained | 90–170 MB | ❌ 严重超标 |
| self-contained + 裁剪 | 40–90 MB（`[待验证]`，WinUI 3 对裁剪支持有限） | ❌ 超标 |

**体积构成（framework-dependent，`[待验证]`）**：
- 应用 dll + 资源：3–8 MB
- Windows App SDK 依赖 dll（`Microsoft.WindowsAppRuntime.*`）：8–15 MB
- 图标 / 种子快照 / 本地化资源：2–5 MB
- 余量：2–5 MB

> **读法**：NFR-1.4 在 framework-dependent 下**可以达标**，前提是运行时由系统提供。若产品不接受「用户机器可能缺运行时」，就只能 self-contained 并接受体积超标——这是 Q-6 的实质内容。

### 3.5.4 预算 → 实测方法

| 指标 | 采集方法 | 采样窗口 | 判据 |
|---|---|---|---|
| WS / PM | `Get-Process -Name githubstore-ui` 读 `WorkingSet64`/`PrivateMemorySize64` | 5 min 稳态，1 s 采样 | 取 P95；回归斜率 <1 MB/min 视为稳态 |
| 安装器子进程峰值 | 按进程名（`msiexec` 等）单独记录 | 安装全过程 1 s 采样 | 仅报告，不计入 NFR |
| 句柄/线程 | `Get-Process` 读 `HandleCount`/`Threads.Count` | 单点 + 5 min 峰值 | 超上限即失败 |
| 冷启动 | ETW 进程创建时间 → 首帧可交互（`DispatcherQueue` 打点） | 冷启动 ×3 | P95 ≤3.0 s |
| 首屏列表 | 窗口可见 → 列表渲染完成打点 | ×5 | ≤1.5 s |
| 搜索端到端 | 按键 → 结果渲染完成（含防抖） | 200 次 | P95 ≤50ms（不含防抖） |
| 滚动帧率 | 快速滚动 30s，采集掉帧数 | ×3 | ≥45 fps |
| 托盘态回归 | 关窗 → 30s 后测稳态；再点托盘打开 → 测重建耗时 | 反复 20 次 | 无句柄线性增长；重建 ≤1.0 s |

**PowerShell 脚本（单进程口径）**：

```powershell
$name = 'githubstore-ui'
$samples = 1..300 | ForEach-Object {
    $p = Get-Process -Name $name -ErrorAction SilentlyContinue
    if ($p) {
        [pscustomobject]@{
            WS_MB   = [math]::Round($p.WorkingSet64 / 1MB, 1)
            PM_MB   = [math]::Round($p.PrivateMemorySize64 / 1MB, 1)
            Handles = $p.HandleCount
            Threads = $p.Threads.Count
        }
    }
    Start-Sleep -Milliseconds 1000
}
$samples | Measure-Object WS_MB,PM_MB,Handles,Threads -Maximum -Average |
    Select-Object Property, Maximum, Average
```

## 3.6 低占用工程手段清单

### 3.6.1 内存

| 手段 | 具体做法 | 预期收益 | 风险 |
|---|---|---|---|
| **列表虚拟化** | `ItemsRepeater` + `ItemsRepeaterScrollHost`（不用 `ListView` 的重型容器） | 高（1000 条从数百 MB 降到几十 MB） | `ItemsRepeater` 无内置选择/键盘导航，需自己实现可达性 |
| **延迟加载 XAML** | `x:Load` 标记非首屏区域（详情页的 README、更新历史、截图区） | 高（首屏不必构造全部视觉树） | 延迟加载区域内的动画/绑定行为有差异 |
| **图片按尺寸解码** | `BitmapImage.DecodePixelWidth` 设为显示宽度；图标多尺寸缓存 | 中高（避免 512px 图解码到 32px 槽位） | 缩放窗口时需重新解码 |
| **图标内存上限** | 内存 LRU 上限（如 300 个），超出回落到磁盘缓存 | 中 | 滚动过快会频繁回读磁盘 |
| **隐藏时卸载视觉树** | 见 §3.5.2 方案 B | 高（托盘态） | 重建耗时 0.5–1.0s |
| **不引用不需要的框架模块** | 不用 `WebView2`、不用 Media/Compass 控件 | 中（只是引用就会加载模块） | — |
| **GC 配置** | 桌面小应用用 **Workstation GC**（默认）+ 并发 GC；**不要**开 Server GC | 中（Server GC 为吞吐设计，堆更大） | 大批量解析时可能更慢 |
| **对象池** | `ArrayPool<byte>` 用于下载/哈希缓冲 | 中（减少大对象堆碎片） | 忘记归还等于泄漏 |
| **避免大对象堆（LOH）** | 不把整个文件读成 `byte[]`；用流式 + `IncrementalHash` | 高（LOH 碎片是 .NET 应用内存增长的常见原因） | — |

### 3.6.2 启动

| 手段 | 具体做法 | 预期收益 |
|---|---|---|
| `PublishReadyToRun` | 发布时预编译，减少 JIT | 高（首启动可省 200–500ms，`[待验证]`） |
| 首屏骨架 | 先渲染静态骨架，数据到再填充 | 高（**感知**启动时间大幅下降） |
| 延迟初始化 | SQLite 迁移、目录加载、更新检查全部延后到首帧之后 | 高 |
| 精简 DI | 用裸 `ServiceCollection`，不用 Generic Host（避免启动一堆后台服务） | 中 |
| 资源按需 | 不把所有图标一次性打进内存 | 中 |
| **不要** 用 `PublishSingleFile` | 释放到临时目录可能拖慢首启动（`[待验证]`） | — |

### 3.6.3 运行时 CPU / 磁盘

| 手段 | 做法 | 判据 |
|---|---|---|
| **无定时器轮询** | 事件驱动；相对时间由单个 60s 定时器驱动且窗口隐藏时 `Stop()` | NFR-1.7 |
| **防抖搜索** | 200ms 防抖 + IME 组字期间不查询 | NFR-2.1 |
| **进度节流** | `IProgress` 回调合并到 ≤20 次/秒 | UI 线程不被打满 |
| **日志** | 按日滚动、单文件 ≤5MB、保留 7 天；release 默认 `Information` | NFR-1.5 |
| **缓存 LRU** | 磁盘缓存上限 512MB（可配），启动时清扫 | NFR-1.5 |
| **HTTP 条件请求** | `If-None-Match`，304 不重新解析 | 省流量与 CPU |

**关于压缩/混淆壳**：**不采用**。体积收益有限，但会触发杀软启发式误报（抬高 RISK-005），且拖慢启动。

## 3.7 应用自更新与分发

非打包（unpackaged）应用没有 MSIX 的自动更新，必须自己实现。

### 3.7.1 更新流程

```
1. 检查：GET releases/latest → 比对版本
2. 下载：新版本到 `%LOCALAPPDATA%\GitHubStore\update\`
3. 校验：SHA256 + Authenticode（WinVerifyTrust）
4. 准备：解压到不可变 `versions\<version>\` 并复校
5. 应用：启动已签名、只接受本地已验证 plan 的 `githubstore-updater.exe`
     ├─ updater 等待主进程退出
     ├─ 原子切换 current 指针/启动器目标到新版本目录
     ├─ 启动新版本并等待健康确认
     └─ 失败则把 current 切回上一版本
6. 清理：健康确认后延迟删除过旧版本目录
```

### 3.7.2 两个实现方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 自身双阶段 | 主程序以特殊参数启动新实例再替换当前目录 | 少一个二进制 | 新实例自身也从待替换目录运行，文件占用、崩溃恢复和防参数滥用复杂，不采用 |
| **B 独立 updater.exe（采用）** | 极小、单用途、独立签名的更新器切换不可变版本目录 | 能在主程序退出后操作；职责和恢复边界清晰 | 多一个需签名与审计的二进制 |

**裁决：方案 B**。updater 不联网、不解析软件源、不接受任意命令或路径；只读取主程序已落盘并签名/鉴权的更新计划，复核目标位于固定版本根目录且新产物签名有效。单进程约束指业务应用只有一个常驻进程，不禁止短时运行的受限更新器。

### 3.7.3 更新的安全要求（与 docs/07 红线一致）

1. **必须校验签名**：新版本 exe 必须由发布者证书签名且有效。**没有签名或签名无效 → 拒绝更新**，不存在「仍要更新」按钮。
2. **必须校验哈希**：`checksums.txt` 中声明的 SHA256 必须匹配。
3. **防降级**：新版本版本号必须 > 当前版本（回退只在人工支持场景提供）。
4. **原子性**：替换失败必须能完整回滚（备份目录 + 校验）。

### 3.7.4 分发形态

| 产物 | 内容 | 体积（估算） |
|---|---|---|
| `GitHubStore-Setup-x64.exe` | 安装器（检测运行时 → 解压 → 写注册表/快捷方式） | 20–35 MB |
| `GitHubStore-Portable-x64.zip` | 绿色版（解压即用，不写注册表） | 15–30 MB |
| `checksums.txt` | SHA256 清单 | <1 KB |
| `.sig`（可选） | minisign/cosign 签名 | <1 KB |

**安装器自身也可以被 winget 分发**（Q-5），此时 `GitHubStore` 会成为 winget 包——这不冲突，因为我们做的是「自己分发自己」，与被安装的第三方包无关。

## 附录 A：已否决的候选方案

### A.1 v0.2 的「WinUI 3 + Go 双进程」方案（已否决）

**内容**：`githubstore-ui.exe`（C# / WinUI 3）+ `githubstore-core.exe`（Go）+ `gs-elevate.exe`（Go，提权）+ 命名管道 IPC。

**否决理由**：
1. **用户明确要求 C# 写业务逻辑**，Go 核心的前提不成立。
2. 双进程带来的全部复杂度（IPC 协议、帧格式、握手、版本协商、重连、背压、双产物签名、双套崩溃上报）在单栈方案下**没有对应收益**。
3. 单栈调试体验远优于跨语言调试。

**被放弃的好处（诚实记录）**：
- **进程级崩溃隔离**：v0.2 里安装器或核心崩溃不影响 UI。
- **跨平台可能**：Go 核心理论上可移植到 Linux/macOS。
- **托盘态 30–50 MB**：靠「托盘归 Go、UI 关闭即退出」实现，单进程做不到。

### A.2 v0.1 的「Wails v2（WebView2 + Go）」方案（已否决）

**否决理由**：用户要求 WinUI 3 原生界面。Wails 渲染的是 HTML/CSS，非原生控件，无障碍与 DPI 表现不如 WinUI 3，且需依赖 WebView2 Runtime。

### A.3 其他 Go UI 框架（已否决，仅作记录）

| 框架 | 渲染方式 | 否决理由 |
|---|---|---|
| Fyne | 自绘（OpenGL） | 非原生观感；中文输入法支持差；内存 80–150MB |
| Gio | 自绘 | 成熟度低；无原生控件 |
| walk | Win32 封装 | 维护活跃度低（`[待验证]`）；仅 Windows |
| webview_go / lorca | WebView | 同 Wails 理由；lorca 依赖外部 Chrome |
| Bubble Tea | TUI | 无 GUI |
| 纯托盘 + 系统浏览器 | 无 UI 进程 | 无法满足商店类交互（列表/详情/向导） |

> **说明**：这些方案在 v0.1 曾作为候选详细对比。用户指定 WinUI 3 + C# 后，整个「Go UI 框架」问题域消失，故压缩为一张否决表。
