## 2. 结构优化：先整理模块，再决定拆项目

保持单进程、轻量 DI 和 MVVM，按实际职责逐步整理：

- 把 Markdown 模型与解析器移到可直接引用的纯逻辑位置，渲染留在 App，减少测试项目链接 App 源码。
- 收拢共享分类、路径规则、能力状态与错误码映射，减少目录实现与 Mock 重复。
- 评估将注册表和进程适配下沉到 Platform.Win32；若让它引用 Core 契约，需同时修订当前架构约束，Core 仍不反向依赖平台。
- ViewModel 专注交互状态，服务负责传输、持久化和进程生命周期；异步操作应可等待、可取消并隔离旧结果。
- GitHub 与 winget 可共用展示模型，继续保留各自来源身份、版本与下载语义，避免自动合并安装身份。

## 3. 测试与验收怎么补

围绕新增能力和失败模式补证据，已有通过数量不作为交付目标：

| 层级 | 待补范围 |
|---|---|
| 服务 / 装配 | 保存后设置实际生效、下载续传与代理、缓存租约和清理边界、安装器参数与退出后的完成判定 |
| UI | 下载复用与清理反馈、取消重试、UAC 拒绝、卸载提前返回、配置分区保存与重启恢复 |
| 设备 / 网络 | x64 Release、ARM64、真实服务端点及多种第三方安装器；仅用专用测试软件或可恢复环境 |

记录源码版本、配置、设备/运行时、输入、预期和实际结果，验证失败应中止脚本。最近一次成功产物不能证明之后的改动已经通过。

## 4. 性能优化应如何做

先固定 Release、运行时、目录规模、Markdown/图片加载和窗口状态，再采样启动耗时、工作集、Private Bytes、CPU、线程和句柄。优先检查重复渲染、列表虚拟化、未展开详情构建、语言切换重建和图片解码。

测量需说明 CPU 的单核/整机口径，并区分工作集与 Private Bytes；强行 GC、最小化窗口或压低工作集不能替代实际优化。
